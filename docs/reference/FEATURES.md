# Features — catalogue fonctionnel

> Inventaire exhaustif de **ce que fait l'app** du point de vue produit : chaque feature, son entrée, son flow, ses états. Compagnon fonctionnel de [`ARCHITECTURE.md`](ARCHITECTURE.md) (le _comment_ technique) et de [`ROUTES.md`](ROUTES.md) (la carte des écrans).
>
> Tout est **mocké** : pas de backend, aucun appel réseau de l'app (seuls le DS, ses icônes et des images d'exemple viennent d'un CDN). Presque rien n'est persisté : quelques préférences en `localStorage`, des handoffs en `sessionStorage`, et les styles / créations de l'Image Generator en `localStorage` + IndexedDB ([`STORES.md` § Persistence](STORES.md#persistence)). Les « analyses », requêtes connecteurs, envois de bug/feedback et générations sont simulés par des timers. Les copies UI citées sont **verbatim** du code.

## Le pipeline

Archie transforme des **Sources** en **Ideas**, puis en **Drafts** (posts), puis en posts **planifiés** — le tout depuis un chat conversationnel.

```
Source → Idea → Draft (post) → Schedule
   │                          ▲
   └── vidéo → Clips ─────────┘  (les clips deviennent aussi des drafts)

Listening source → Topic ──→ (chat) ──┘   (le Topic Feed, voir §17)
```

Le **Topic** est un embranchement amont **optionnel** : Archie n'attend plus qu'on lui donne une source, il en propose une. Une Idea peut toujours venir directement d'une Source.

Vocabulaire : un **Playbook** (label UI) = un **Context** (code/store). Voir [`GLOSSARY.md`](GLOSSARY.md).

## 1. Chat & assistant

Surface principale, sur `#/session/:id` ([`screens/session.js`](../../src/screens/session.js), découpé par sujet dans [`screens/session/`](../../src/screens/session/)). Un panneau assistant plein-largeur : thread scrollable en haut, composer docké en bas. L'état du thread est un store en mémoire par session ([`assistant.js`](../../src/assistant.js)), sans persistance.

### Composer

Markup : [`session/composer.js`](../../src/screens/session/composer.js).

- **Champ** : textarea auto-size 2 lignes, placeholder _« Ask a follow-up, or refine a draft… »_ — sur un chat vide, _« Paste a link, drop a file, or tell me what to post… »_ ; Playbook qui ne m'est plus partagé → lecture seule, _« This Playbook isn't shared with you anymore. … »_. Toolbar : **Add** · **Reference (@)** (absent d'un chat neuf qui n'a rien à référencer, désactivé tant qu'il n'y a ni source prête ni idée) · **Playbook** · **Send** (orange). Hint _« Enter to send · Shift+Enter for new line · Drop a file to attach a source »_ ; sur un chat neuf (flag `newChatHero`), la ligne ne porte que le lien Admin.
- **Envoi** : Send, **Enter**, ou **Cmd/Ctrl+Enter** ; **Shift+Enter** = newline.
- **Menu Add** : _Add PDF · Add video · Add URL · Paste text_ — puis _Repurpose a top post_ · _Pick from the Topic Feed_ — puis (flag `connectors`) le sous-menu **Connectors** (les connectés + « Browse connectors »). En démo : _Add demo PDF…_, _Add demo text_.
- **Contrôle Playbook** : sur chat neuf = `.ap-select` sélectionnable (+ « Create a Playbook ») ; sur chat actif = indicateur statique. Sous `playbookWorkspace` il **n'est plus rendu du tout** : la question a été posée dans la rail avant que le chat existe, et la rail nomme la marque une rangée de chrome plus haut (§14). Send est en `margin-left: auto`.
- **@ Reference (mentions)** : picker flottant listant sources prêtes + idées ; pick → pill (tag du kind). Nav clavier ↑/↓/Enter/Esc. Chips gérés par [`composer-mentions.js`](../../src/composer-mentions.js).
- **« / » commande (connecteurs)** : liste les connecteurs connectés en action-dropdown ; pick → attache au composer.
- **Chip connecteur** : demander un connecteur attache un chip removable + swap placeholder _« Ask {name} anything… »_. ([`composer-connector.js`](../../src/composer-connector.js))
- **Status bar** : un slot réconcilié au-dessus du composer (`computeComposerStatus`). Sous `newConversationStyles` (ON), il ne nomme que le travail de fond (_« Analyzing <fichier>… »_, extraction d'idées / de clips) : une réponse en cours a déjà sa pill dans le fil, juste au-dessus. Gris in-progress (loader + label, _« Working on N things… »_ à plusieurs) prioritaire sur vert « ready » (_« N drafts ready to review »_ + **Review**, _« N ideas ready »_ + **View ideas**) — ces barres vertes seulement avec `contentPanel` OFF. Le même slot porte la bande du post plan (ci-dessous). Animations enter/exit, reduced-motion aware.
- **Drag & drop** : déposer un fichier sur le panneau lance l'upload (toast _« Uploading "<fichier>"… »_) ; fichier refusé → modale Add source sur Upload.
- **« Admin: preview in chat »** (icône `ap-icon-illuminati`, flag `chatPreviewTool`, **ON** ; [`chat-gallery.js`](../../src/screens/session/chat-gallery.js)) : un lien dans la ligne d'aide sous le composer, qui ouvre un `.ap-action-dropdown` vers le haut, avec recherche, en cinq sections — **Components** (un exemple de chaque turn que le fil sait afficher, posté directement via `assistant.js`), **Typed asks** (les demandes que le routage reconnaît, envoyées par le vrai submit du composer : batch, launch, compare, schedule…), **Edit a draft** (shorter, warmer, emojis, CTA, translate…), **Mention someone** (4 entrées, flag `draftMentions`), **Flows** (draft from an idea, top posts, Topic Feed, connecteur, video intake, connect an account…). Une entrée dont la condition manque (flag OFF, pas d'idée, pas de vidéo…) est désactivée et dit pourquoi. ⚠️ Le catalogue est tenu à la main : un nouveau variant de turn ou une nouvelle route s'y ajoute aussi.

## 2. Sources

Store [`sources-stream.js`](../../src/sources-stream.js) : les sources **par session** (`Map(sessionId → Source[])`) + la machine à états, et un pool **global** d'uploads en cours que la modale lit en entier. Lu par session via [`library.js`](../../src/library.js) `getSources`.

### Ajouter une source — modal ([`add-source-modal.js`](../../src/components/add-source-modal.js))

Dialog mono-méthode, titré par sa méthode (_Attach a file · Add a URL · Paste text · Add a source_). Entrées : panneau Sources « Attach a source », menu **Add** du composer, starters du chat neuf.

- **Upload** : dropzone _« Drop files here, or »_ / _« PDF, Word, text, video, audio, or images · up to 100 MB each »_. Accepte `.pdf,.doc,.docx,.txt,.md,.mp4,.mov,.mp3,.wav,.m4a,.png,.jpg,.jpeg`. Multi-fichiers. Ligne par fichier : _« Uploading NN% »_ → pill bleu **Processing** → pill vert **Ready**.
- **URL** : label _« Paste a URL »_, placeholder `https://example.com/article`. Reconnaissance de service live (logo + _« I recognized a <service> link. I'll import it. »_). Un domaine nu reçoit `https://` ; validation au blur _« Enter a web address, like acme.com/blog. »_. Toast _« Link added. I'm reading it now. »_. Lien connecteur non connecté → connect-prompt in-chat.
- **Paste text** : textarea + _« Paste from clipboard »_, compteur live _« N characters »_. Toast _« Text added. I'm reading it now. »_.
- **Connectors** (flag `connectors`) : onglet de la modale : connecteurs connectés + « Browse » ; sub-écran browse avec cases par doc, « Select all », dossiers _« Folder · imports N files »_ (cap `FOLDER_BATCH_CAP` = 8), « Import N sources ».

### Machine à états du traitement

Classification par extension ([`file-kinds.js`](../../src/file-kinds.js) + `classifyFile`) : PDF, Word, Text, Video, Audio, Image. Rejette un type inconnu (_« Couldn't add <file>: I can't read that file type. Use PDF, Word, text, video, audio, or images. »_) et > 100 MB (_« <file> is over 100 MB. Compress or split it, then try again. »_).

```
upload (uploading, progress 0→100% ~2s)
  → Source status:"Processing" signal:"Pending"
  → [ticker granulaire ~200ms] Extracting content → Reading content → Identifying ideas → Mining hooks & quotes → Finalizing
  → après ~6s : status:"Processed" + signal aléatoire
```

- **URL / Paste / Connector** : sautent l'upload, directement en Processing.
- **Ticker** : pour Video/Audio, « Reading content » s'affiche _« Transcribing audio »_. Barre fine + _« <stage> · ~Ns left »_ + pill mermaid « AI is working ».
- **Signals** (`randomSignal`, skew Medium) : **High** (orange) / **Medium** (tagOrange) / **Low** (grey). Sources réutilisées → signal « Reused ».
- **Rien n'est extrait à l'arrivée** (parité prod) : toute source processée a `ideaCount` = 0 et `use: "waiting"` jusqu'à la réponse à _« What should I do with it? »_ (§1, `askSourceUse`). Les idées n'existent qu'après _Find post ideas_.
- **Usage** (`use`, à côté du `status` binaire Processing / Processed) : `waiting` _Waiting for your answer_ (orange) · `ideas` _Used for ideas_ · `post` _Used in a post_ · `clips` _Used for clips_ (vert) · `set_aside` _Set aside_ (grey) — `SOURCE_USE_LABEL` / `SOURCE_USE_TONE`, setter `setSourceUse`. Affiché en `.ap-status` dans la carte d'intake du fil tant que la source n'a rien produit, et dans la sous-ligne de la source card. Les seeds, Topics et top posts n'ont pas de `use`.
- **Toasts** : _« <name> ready »_ pour tous.
- **Cancel** : `cancelUpload` jusqu'à Done.

- **La liste** : le batch se lit comme un calendrier éditorial, dans **une seule liste encadrée** (filet grey-20, rayon carte), avec des filets entre les lignes. Les lignes sont **triées par date**. Le post est à gauche parce que c'est l'objet qu'on reconnaît avant de décider quand il part. Les dates à droite forment une colonne qu'on relit d'un coup d'œil, juste au-dessus du primaire. La vignette et l'heure sont cliquables : elles ouvrent le sélecteur natif via `showPicker()` sur un `datetime-local` caché sous l'heure, et l'heure passe en bleu au survol.

Son tooltip et son `aria-label` disent _« LinkedIn's best time »_ (_« … in the morning »_ avec un moment de la journée). **Un seul concept, le _best time_ du réseau, et un seul traitement.** ⚠️ Une version distinguait _« Best window »_ (en pastille) de _« Best hour »_ / _« Best morning hour »_ (en texte), pour un seul et même concept : _« y'a pas de best hour ou best day, c'est best time tout simplement »_. Le tooltip ne cite pas non plus les meilleurs jours du réseau, parce que sur une date prise hors de ces jours par le rythme, il se contredisait.

Les drafts de démo `post-acme-1/3/4` portent une image, un carrousel et une image.

Le **crayon** (_Change date or time_) est dans la cellule date, à côté de l'heure, **toujours visible** (grey-80 au repos, bleu avec l'heure au survol) : modifier la date est le geste principal de la modale après la confirmation, il ne peut pas dépendre du survol. Ensuite, des vignettes sur un rail vertical, avec des cartes de draft détachées à droite : _« ça flotte beaucoup trop »_, rien ne tenait la date à son draft. C'est le cadre commun et les filets qui tiennent les lignes.
  - En dessous de 600px, « Quand » passe sous « Quoi », séparé par un filet horizontal.
- **Hauteur constante, ligne ET dialog** : le sous-titre du calcul (_« Finding the best time for each draft… »_) et celui du résultat (_« I picked the best time for each draft… »_) ne diffèrent que d'un verbe, pour se couper pareil. ## 9. Playbooks

Un Playbook capture business summary, audience, goals, voice/style, brand identity — la **fiche d'identité d'un émetteur (marque ou voix) et de son cadrage éditorial**. Ce qu'il est et ce qui n'a jamais le droit d'y entrer : [`CONCEPTS.md` §1](CONCEPTS.md#1-le-playbook). Ci-dessous, ce qu'il fait. Stores/vues : [`contexts-store.js`](../../src/contexts-store.js), [`context-builder.js`](../../src/context-builder.js), [`playbook-view.js`](../../src/playbook-view.js), [`playbook-rosters.js`](../../src/playbook-rosters.js), [`context-mock-analysis.js`](../../src/context-mock-analysis.js), [`languages.js`](../../src/languages.js).

### Library (`/contexts`, ou l'onglet **Playbooks** de `/home` — [`screens/home.js`](../../src/screens/home.js), [`screens/home/lists.js`](../../src/screens/home/lists.js))

**`/contexts` (flag `playbookWorkspace` OFF) — une grille de cartes.** **Pas de `h1` dessiné** (DS page-patterns P1–P4 et organism O3, comme le Topic Feed et Connectors) : la topbar nomme la route et porte le primaire de la page, **« Create a Playbook »** à droite (`setTopbarActions`, absent tant que la liste est vide — l'état vide porte alors son propre CTA). La page ouvre sur la phrase du concept (`concept-lead`), puis les onglets de propriétaire (P4, sous `playbookSharing`), puis une barre d'outils, **la recherche en premier, à gauche** (P3), puis l'infobox des voix à finir (« N Playbooks have voices to finish », flag `voicePerNetwork`). Grille de cartes + ghost card, qui a l'anatomie d'une carte vide (couverture grey-05, la marque Archie à la place du logo, « Create a Playbook » et sa phrase alignés à gauche). Un Playbook sans palette de site prend en couverture **sa propre couleur**, celle de son point dans la rail, au palier -20 ; sans couleur, grey-05. Carte = une fiche de marque, quatre rangées alignées d'une carte à l'autre (subgrid) : **la couverture** (64px, la palette du site en aplats, sinon grey-05 ; un champ, pas une bande — choix de l'utilisateur) avec la vignette de la marque à cheval sur son bord (le logo « Icon » quand il existe, sinon le logo, sinon les initiales) ; Current et la marque de propriétaire en haut à gauche de la couverture ; **le corps** : nom (+ ★ default), la voix en phrase (« Direct, operator-first, specific. »), le brief sur deux lignes ; **trois chiffres**, chacun avec son icône et nommé en texte, 0 compris (audiences · competitors · influencers — les suggestions en attente ne comptent pas) ; **le pied** : l'icône de chat et _« N chats »_ (ou _« No chats yet »_), puis _« Updated {when} »_ ; à droite _« N voices to finish »_ + les réseaux, qui prend alors la place de la date. Hover : **Share** (si `canManageSharing`) · **Edit** (ou **Open**, en lecture seule) · **Duplicate** · **Delete** (si `canDelete`). Clic sur la carte → la fiche. **Sous `playbookSharing`**, des onglets DS trient la grille par propriétaire : **All · Mine · Shared with me**, chacun avec son compteur ; ils n'apparaissent que si au moins un Playbook m'est partagé, et « Shared with me » n'a pas de ghost card (un nouveau Playbook est à moi). Garde : impossible de supprimer le dernier (_« Can't delete your only Playbook. Every chat needs one, so create another first. »_).

**Sous `playbookWorkspace` (§14), le catalogue est l'onglet Playbooks de la home du compte** (§12) : `/contexts` y redirige (`replace` vers `/home?tab=playbooks`, `catalogueRoute()`). Le héro porte le seul `h1` ; la recherche et **Create a Playbook** sont dans la barre d'outils sous les onglets. La page parle des marques où l'on n'est **pas** : `body.account-scope` ([`ROUTES.md`](ROUTES.md) § Deux niveaux de chrome) — pas de rail, une colonne, la topbar réduite à **« Back to {marque} »** — et une seule porte d'entrée : le footer du switcher (**All Playbooks**). La ligne de nav, elle, pointe la fiche de la marque active (§12).

Ce que la tuile porte et que la ligne ne porte pas : les **compteurs**, la **voix en phrase** et la **palette** (la vignette et le dot portent déjà l'identité). Pas de ghost card : `Create a Playbook` est dans la barre d'outils. **Sous le flag, la ligne EST le workspace** : cliquer dessus bascule sur cette marque (`setActivePlaybook`) et ouvre un **chat neuf** dedans (`?contextId=`, pas `/` — la home est un lanceur, le geste est « démarrer », pas « reprendre ») ; la fiche est dans le kebab. ⚠️ L'inverse (le corps ouvre la fiche, un lien `Switch` porte la bascule) a tenu un commit ; décision de l'utilisateur, ne pas le remettre. ### Moteur partagé ([`playbook-view.js`](../../src/playbook-view.js))

Sections éditables inline (une à la fois, Save/Cancel avec snapshot) :

1. **Brief** — Language(s), Business, Primary audience, Content style, Primary goal, Content action, CTA links.
2. **Voice profile** — Part by part ⇄ In my own words. Part by part = les cinq parties (`voiceSummary` · `voiceAlways` · `voiceNever` + `voiceAvoid` · `voiceByPost` · `voiceSometimes`), chaque liste éditée règle par règle (un cas = « Kind of post » + la règle ; les exemples tirés des posts restent affichés sous la règle, non éditables). Pas de switcher par langue sur Voice : les cinq parties sont agnostiques de la langue (limite assumée) ; seul le CTA reste par langue. Dropdown « Learn from… » (My posts · Documents…).
3. **Branding** — **Logos** (galerie + un défaut), Colors (hex + rôle), Typography, Personality, Visual rules.
4. **Competitors** — voir ci-dessous.
5. **Influencers** — voir ci-dessous.

L'onglet **Image generation** n'est pas une section : il appartient au module Image Generator et s'enregistre au changement (voir « Kit de marque »).

**Les logos** sont la première ligne de Branding, parce que c'est la pièce la plus concrète de l'identité visuelle et la seule que le générateur d'images cuit dans les pixels.

**Un SET, pas un logo.** Un site en porte plusieurs — le lockup d'en-tête, la version inversée du footer, l'icône carrée, le favicon — et ils sont tous légitimement « le logo ». Donc `brandLogos: Array<{ id, label, url, variant? }>` (le set) + `brandLogo` (**l'URL du défaut**, pas un id ni un getter : l'aval — header, logos du module Image Generator (`playbook-brand.js`, `defaultLogoUrl`) — lit `brandLogo`, et `snapshotEditable` fait un aller-retour JSON qui écraserait un getter). `normalizeBrandLogos()` dans [`contexts-store.js`](../../src/contexts-store.js) tient l'invariant : `brandLogo` est **toujours** une des URLs du set, ou `""` quand il est vide — un contexte qui ne portait que `brandLogo` devient un set d'une entrée. Le compteur `brandLogoSeq` vit en haut du fichier parce que le seed appelle le normalizer à l'init du module, où un `let` déclaré à côté de sa fonction serait encore dans sa TDZ.

**La galerie.** Vignettes carrées + label dessous. Le défaut porte un badge check et le tag `Default`. En **lecture** on montre tout le set, pas seulement le défaut — les vignettes sont alors des `<span>`, rien n'est cliquable. En **édition** chaque vignette devient le contrôle de sélection, avec une poignée de suppression.

Retirer le défaut passe la main à ce qui reste ; vider le set fait retomber le header sur les initiales. Le défaut est stocké **par URL et jamais par index** — un index pointerait silencieusement sur une autre marque dès qu'on supprime celle du dessus.

**D'où viennent les marques.** `imageVoice.websites[0].images.logos` : de vraies marques Archie pour une analyse d'agorapulse.com, et pour n'importe quel autre domaine **le favicon résolu depuis ce domaine** (même service que les logos de compétiteurs) — inventer un wordmark pour « foo-bar.com » mettrait dans le Playbook un logo qui n'appartient à personne. `deriveBrandLogos()` lit ce champ, en miroir exact de `deriveBrandColors()`.

Upload = **Add a logo** + input caché, multi-fichiers, `FileReader.readAsDataURL` et non `URL.createObjectURL` — un object URL est éphémère et ne survivrait pas au store. Le label est le nom du fichier sans son extension. Plafond `MAX_BRAND_LOGOS = 8`.

Le défaut **remplace le monogramme d'initiales** dans le header du Playbook (pattern image + jumeau monogramme, swap sur `error`, comme les logos de compétiteurs). Le set repart ensuite dans l'Image Generator (§18).

#### `imageDefaults` — un champ sans surface

`imageDefaults: { imageType, style, refMode }` (trois chaînes, `""` = pas de préférence) est encore normalisé par le store et **pré-rempli à la création** (`imageDefaultsFromAnalysis` dans [`context-builder.js`](../../src/context-builder.js), appelé par `applyAnalysisToDraft` et **pas** par `sectionPatchFromAnalysis`, pour que Re-analyze website ne l'efface pas : le ton du site choisit la famille, l'énergie le membre ; seul `style` est dérivé). Mais **rien ne l'affiche ni ne le lit** depuis la suppression de l'ancien Image Studio (§7) : le module dit lui-même que ce champ « serves the old Image Studio ». Le look d'une image générée est `defaultLook`, réglé dans l'onglet Image generation (§18).

Un Playbook est une **fiche** : chaque section répond à « qui êtes-vous ? ». La config opérationnelle (quelles sources d'écoute tournent, à quelle fréquence) vit dans son propre store, clé par Playbook, et s'édite sur la route qui possède la feature — voir §17. Une section Topics a été essayée puis retirée : une grille d'interrupteurs se lisait comme un panneau de réglages coincé dans un profil. Le champ `ctx.topics` qui la portait est parti avec elle.

### Les cinq parties de la voix

La voix d'un Playbook est faite de **cinq parties** (la taxonomie d'une fiche de voix réelle : « How the Brand sounds / Always / Never / Depending on the post / Now and then »), un seul registre, `VOICE_PARTS` ([`voice-parts.js`](../../src/voice-parts.js)), chacune avec sa ligne `hint`. Elles ont remplacé _Opens with · Closes with · Formatting · Emoji & casing_ (+ Hashtags) partout (2026-10-15).

- **Une règle** = `{ text, examples? }` ; **un cas** (_Depending on the post_) ajoute `when` (le type de post). Les **exemples** sont des lignes des posts de la marque : en lecture, en citations sous la règle ; en édition, affichés, pas éditables. Rendu commun : `voiceItemsHtml`, une boîte par règle (`.voice-rule`).
- **Ce que sont devenues les anciennes parties** : les hooks et closings sont des exemples des règles de _Always_ / _Now and then_ ; Formatting et Emoji & casing des règles d'_Always_ / _Never_ ; les **Words to avoid** vivent dans le bloc _Never_ (une liste du Playbook, `voiceAvoid`) ; les trois mots de la voix chapeautent _How the Brand sounds_. `voiceSummary` retombe sur `voiceProfile.writingStyle` quand il est vide (`baseValue`).

### Une voix par réseau (flag `voicePerNetwork`, défaut OFF)

Le pourquoi et ce qui a été essayé puis retiré : [`DECISIONS.md` § Une voix par réseau](DECISIONS.md#une-voix-par-réseau--une-seule-règle-partout). Ici, ce qui existe.

**Le modèle** ([`voice-parts.js`](../../src/voice-parts.js)). La **default voice est générique** : les cinq parties du Playbook, à plat, liées à aucun réseau. Chaque réseau en est une **déclinaison** : il a **sa voix à lui** (`voiceByNetwork[réseau]`, une voix complète + `optimizedBy` : `learned` — `learnedFrom`, `postCount` — ou `you`) ou écrit dans la **default voice**. `networkVoice(ctx, net)` → `own` | `default` (`chosen` : la default voice a déjà été choisie dans l'étape Voice — stockée comme `optimizedBy: "brand"` — pour ne pas redemander) | `brand` (flag OFF). Une règle propre au réseau porte `adapted: true` et le tag « For X » (`voiceNetTagHtml`).

**Quels réseaux.** `voiceNetworks(ctx)` : les réseaux dont un compte est connecté **maintenant** (tous, ceux du Playbook d'abord — `connectedNetworks`), **vide s'il n'y en a qu'un**. Un seul réseau (`onlyNetwork`) : la default voice est la sienne — pas de status card de voix sur ses drafts (`draftVoice` → `null`), pas d'étape Voice, pas de « Finish your voices », pas d'intro, rien au compteur de la sidebar ; la revue Voice de la création dit « How your X posts sound. ». Sur la fiche, d'autres réseaux s'ajoutent quand même par _Add a voice for another network_.

**Les mots** : la **default voice** · la **X voice** (« Network voices ») · **Add to Voice profile** (enregistrer ce qu'Archie propose). Jamais « voice learned », « use this voice » ni « optimize ».

**Donner sa voix à un réseau — les mêmes choix partout** (`voiceChoices`, [`network-voice-flow.js`](../../src/network-voice-flow.js)) :

1. **Learn from {compte}'s posts** (≥ 10 posts, `canLearnFrom`)
2. **Adapt my default voice for X** — sans source : Archie garde la default voice et ajoute ce qui marche sur le réseau (longueur, mise en page, hashtags) ; `adaptNetworkVoice`, `ADAPTED_FROM` (mock : les mêmes adaptations que l'apprentissage, [`mocks/voice-networks.js`](../../src/mocks/voice-networks.js)).
3. **Learn from a document**
4. **Write it myself** — l'onglet du réseau en édition, depuis la default voice ; **chaque partie y pose sa question** (« How do you sound on X, in a sentence? », « What would you never do on X? »… — `partQuestion`). ⚠️ Il a absorbé **A few questions** le 2026-11-04 (le dialog, sa version chat et `interviewNetworkVoice` supprimés) : ne pas les remettre.
5. seulement quand un draft attend : **Use my default voice** (`useDefaultVoice`).

### Competitors

Le marché contre lequel Archie positionne la marque. Champs sur le Playbook : `competitors: Array<{ id, name, description, websiteUrl, socials:[{network,url}], logo?, suggested? }>` et `dismissedCompetitors: string[]`. Rendu par [`playbook-rosters.js`](../../src/playbook-rosters.js) (avec Influencers, `ROSTERS`), que `playbook-view` appelle avec un `rosterCtx`.

**Deux états, jamais confondus.** `suggested: true` = **proposition en attente** d'Archie, qui ne fait PAS partie du Playbook. Tout ce qui compte les compétiteurs (grille active, compteur de l'onglet, chiffres de la carte du catalogue) ignore les pending ; seul le bac « Suggested by Archie » les lit.

|                         | Actif                               | Suggéré (pending)                                                             |
| ----------------------- | ----------------------------------- | ----------------------------------------------------------------------------- |
| Groupe                  | **« Your competitors »** + compteur | bac **« Suggested by Archie »** + compteur, fond creusé sous la grille active |
| Carte                   | bordure pleine, surface blanche     | bordure **pointillée**, actions incluses dans la bordure                      |
| Actions                 | remove (en edit scope)              | **Add** / **Dismiss** par carte + **« Add all »** dans l'en-tête du groupe    |
| Compté dans le Playbook | oui                                 | non                                                                           |

- **Grille de cartes** — tuile logo, nom, domaine, blurb sur 2 lignes, badges réseaux. Clic sur une carte → modale détail (`.ap-dialog`) : Name, Website, Description, Social profiles (select réseau + URL). Éditable quand la section est en edit scope, sinon lecture seule + liens réseaux cliquables. Pour une proposition, le footer de la modale offre **Dismiss** / **Add to Playbook** au lieu de Done.
- **Accepter / écarter** — dispo en **lecture** (pas besoin d'ouvrir l'éditeur de section, c'est tout l'intérêt du bac). Add → `delete suggested`, la carte rejoint la grille active. Dismiss → la carte disparaît et sa clé part dans `dismissedCompetitors`, donc **Archie ne la repropose jamais**. Hors edit scope les deux commitent directement ; en edit scope c'est le Save de section qui commite.
- **Favicon auto-extraite** — jamais stockée : résolue à partir du domaine via un service de favicons au render. Un `<img>` qui échoue bascule sur une **tuile monogramme** teintée déterministiquement depuis le nom, via un listener `error` en phase **capture** (`error` ne bulle pas) posé dans `mount()`.
- **Découverte** — bouton **« Discover competitors » / « Discover more »** dans le head de section : skeleton scoped à la section (`ROSTER_SCAN_MS`, 1,6 s, pas le loader plein écran) → merge de `discoverCompetitors(url, { exclude })` où `exclude` = les compétiteurs présents (actifs **et** pending) + `dismissedCompetitors`. Save élague les fiches restées entièrement vides et les lignes sociales sans URL ; `suggested` est **conservé** — une proposition non acceptée reste en attente au lieu d'être adoptée silencieusement.

### Partage (flag `playbookSharing`, défaut OFF) — « §9bis »

Le problème : dans une org multi-users, N personnes créent chacune leur Playbook pour la **même marque**, personne ne sait laquelle fait autorité, et le travail part avec celui qui quitte l'entreprise. Les seeds le mettent en scène : `Acme · Q2 marketing` (à moi) et `Acme · Developer relations` (à Sam Rivera) sont deux fiches pour Acme.

Les trois portées ont chacune leur seed : `Acme · Q2 marketing` est **à l'org** (vu du propriétaire), `Customer stories` est **nommément** à Sam + Léa et **liée au profil LinkedIn** (donc son picker grise des collègues), `Acme · Developer relations` est reçu **nommément** de Sam (lecture seule). L'org compte 12 membres, `ORG.memberCount` en dérive.

**Trois portées, et la distinction qui les sépare est fixe ⇄ dynamique.** Un Playbook est `scope: "personal"`, `"members"` (une liste **fixe** de collègues, dans `sharedWith`) ou `"organization"` (une liste **dynamique** : toute l'org, arrivées comprises). Un `members` **vide n'est pas partagé** — il ne touche personne, et toute la portée d'un manager pend à ce prédicat.

⚠️ **Ça a vécu deux semaines en binaire** (pas de liste de destinataires, pas de people-picker). La doc produit a trois états dans **toutes** ses versions (§5.1, §5.3, §6.1, lot L2) et l'arbitrage qui en avait retiré un n'était écrit nulle part — donc la doc a gagné (audit du 2026-09-10). Ne pas re-supprimer le partage nommé sans l'écrire dans la doc d'abord.

**Un Playbook lié à un profil social ne touche que qui touche ce profil** (doc produit §7). `profileBlockFor()` passe **avant** tout autre test dans `canView`, et le picker garde le collègue bloqué dans la liste, **désactivé, avec la raison** (« No access to {compte} ») : retirer la ligne laisserait le propriétaire chercher son collègue. La permission est **celle d'Agorapulse** — `profiles` par membre dans [`org.js`](../../src/org.js), `"all"` ou une liste d'ids — jamais stockée sur la fiche ([`CONCEPTS.md`](CONCEPTS.md) §6). **Fail open** quand le profil ne se résout pas (rien de connecté, id périmé) : une contrainte invérifiable ne doit pas verrouiller une fiche.

**Champs sur le Context** (normalisés par `normalizeOwnership()` dans [`contexts-store.js`](../../src/contexts-store.js), dans `addContext` **et** sur le seed qui le bypasse) : `ownerId`, `scope`, `sharedWith: string[]`, `history: Array<{ id, actorId, action, when }>` (capé à 12, `MAX_HISTORY`). `sharedWith` **survit** au passage en privé et retour — donc seul `scope` décide qui est dedans, et `normalizeScope` est une `function` et non un `const` parce que le seed normalise pendant que le module s'évalue encore. L'identité et l'org vivent dans [`org.js`](../../src/org.js) — **CONFIG, pas des mocks** : un utilisateur `new-alt` a lui aussi un nom et une organisation, même split que `ff-catalog.js` vs `mocks.js`.

**Les droits vivent dans [`playbook-access.js`](../../src/playbook-access.js), pas dans le store.** Le store continue de tout renvoyer à tout le monde, délibérément : un chat dont le Playbook a cessé d'être partagé doit encore pouvoir le **nommer**, donc lire une fiche qu'il ne peut plus ouvrir. Le store tient les faits, ce module tient les droits, et `revokedContextFor()` est le seul autorisé à regarder par-dessus la barrière. `canView` / `canUse` / `canEdit` / `canGovern` / `canDelete` / `canManageSharing` / `canTransfer`, plus `visibleContexts()` / `usableContexts()` / `editableContexts()` que les surfaces substituent à `getContexts()`. **Flag OFF ⇒ tout est permis** — un seul point de court-circuit, `on()`.

|                                   | Propriétaire | Membre, `organization` | Manager, `organization` | Membre, `personal` d'un autre |
| --------------------------------- | ------------ | ---------------------- | ----------------------- | ----------------------------- |
| Voir / utiliser / dupliquer       | ✅           | ✅                     | ✅                      | ❌                            |
| **Éditer le contenu**             | ✅           | ❌                     | **❌**                  | ❌                            |
| Partager / supprimer / transférer | ✅           | ❌                     | ✅                      | ❌                            |

**Éditer et gouverner sont deux droits séparés, et le manager n'a que le second.** Le contenu d'un Playbook est à son propriétaire et à personne d'autre : partagée, la fiche est en lecture seule pour tout le monde, managers compris (doc §5.2). Ce qu'un manager peut faire vit dans **`canGovern()`** — mettre devant l'org ou l'en retirer, transférer, supprimer. `canDelete` / `canManageSharing` / `canTransfer` dérivent de `canGovern`, jamais de `canEdit`. ⚠️ `canEdit` a renvoyé `true` pour un manager pendant deux semaines (un crayon sur chaque section de la fiche d'un collègue) : ne pas y revenir.

Le manager ne voit **que** les Playbooks partagés : une fiche personnelle non partagée reste privée même pour lui. Le rôle se change dans **Admin → Your role** ([`org.js`](../../src/org.js), `localStorage` `archie-org-role`).

Ouvert depuis la carte, le tableau et la fiche. CTA **bleu** : partager est une action de liste routinière, pas une action IA.

Le store et ses trois valeurs sont intacts — c'est l'UI qui cesse de demander au lecteur de nommer un mode.

  - **TOUS LES CONTRÔLES SONT DES COMPOSANTS DU DS, non modifiés.** Le picker de personnes est le **Selection Dropdown** de l'ADS derrière un trigger `.ap-select` (recherche + items cochables + état vide), et l'accès général comme le transfert sont des `.ap-select`. ⚠️ **Une passe en a INVENTÉ deux** (une combobox sans bordure, une switch-row) parce qu'un dropdown ne pouvait pas échapper au dialogue qui scrolle. La réponse est `position: fixed` + coordonnées posées au toggle, pas un composant neuf. **Ne pas fabriquer de contrôle à la main ici.**
  - ⚠️ **`position: fixed` ne se résout PAS contre le viewport dans cette modale.** Les modales centrées portent `transform: translate(-50%, -50%)`, et **un ancêtre transformé devient le bloc conteneur de ses descendants fixed**. `placePopover()` soustrait donc la boîte de la modale. Le panneau bascule **au-dessus** du trigger quand il reste moins de 200px dessous et davantage dessus, se referme au scroll du corps et au clic dehors (`<details>` n'a pas de fermeture extérieure native).
  - ⚠️ **Le corps de la modale est BLANC.** Les modales n'ont pas de fond gris ici : ce qui structure ce dialogue, c'est le chrome propre des contrôles du DS, les intitulés et la liste de personnes à filets.
  - **Le contenu SCROLLE** (`overflow-y: auto` + `min-height: 0` sur `.ap-dialog-content`), ce que les popovers fixes rendent possible. ⚠️ En `overflow: visible`, le footer Cancel / Save tombait sous l'écran, injoignable.
  - **Cocher quelqu'un ne re-render PAS le corps** : le dropdown est un multi-select, il se fermerait à chaque clic en emportant la requête de recherche. `refreshPeople()` ne redessine que la liste (`[data-share-people]`), plus le bouton et l'encart de conséquence. Le `×` d'une ligne fait pareil **et décoche la case correspondante** dans le dropdown. Changer l'accès général, si : c'est structurel, donc `renderBody()`.
  - **La liste `People with access`.** Le **propriétaire y est la première ligne**, marquée `Owner`. La puce **`you` se pose sur la ligne qui est la mienne**, propriétaire ou destinataire. Le `×` de retrait **garde sa place en permanence** et n'apparaît qu'en opacité au survol.

  - **Le picker de transfert est un `.ap-select`** de la même famille, dans la disclosure.
  - **La phrase de rôle** (qui peut lire et écrire avec, et que seul le propriétaire change ce qu'il dit) se pose sous **le contrôle qui définit la portée** : la liste tant que l'accès est sur invitation, la ligne d'accès général dès que l'org entière est dedans. Elle nomme le propriétaire plutôt que « you » : elle était fausse sur l'écran d'un manager.
  - **Save nomme le CHANGEMENT, pas l'état** — « Share with everyone at {org} » / « Share with N people » / « Keep it to myself », et **« Save » grisé** quand rien n'a bougé.
  - **Pas d'autofocus au chargement** : ouvrir le picker d'emblée déplierait son panneau par-dessus le reste avant que le lecteur ait lu un mot.
- **Suppression** — le confirm dit la conséquence quand d'autres en dépendent (partagé à l'org : « They keep their drafts and can still save or schedule them, but I can't draft anything new in them. »), au lieu de « will be removed ».

**Le chat dégradé** (§6.3 du brief produit). Perdre l'accès ne casse pas le chat, ça le **fige** : les drafts déjà écrits restent enregistrables et programmables, rien de neuf ne se génère. Un seul prédicat, `revokedContextFor(session)`, et deux chemins y mènent — la session seedée `s-brightline`, et un manager qui repasse en personnel le Playbook d'un collègue pendant qu'on l'utilise.

- Composer : send `disabled`, textarea `readonly`, hint remplacé par la sortie, et `submitInput()` garde-fou en entrée.

Sur `<body>` et pas sur la racine de la session : le panneau des drafts est du chrome de shell, **hors `#app`**. Un listener plutôt qu'un flag enfilé dans cinq renderers de cartes : les cartes restent ignorantes du partage.
- Choisir un Playbook accessible dans le picker est la sortie : `setHashQuery` refait tourner le handler (comme `startBatchChat`).

**Notification & historique.** Toute action d'un manager sur la fiche d'un autre toaste _« {Owner} will be notified »_ et ajoute une ligne au journal (`appendHistory`, deux appelants : le modal de partage et [`playbook.js`](../../src/screens/playbook.js)). C'est délibéré — la trace est ce que la doc exige (§6.4). Ne pas supprimer le champ ni les appels en croyant nettoyer du mort.

**Ce qui n'est pas fait** (non-objectifs v1) : bibliothèque inter-orgs, versioning, fusion de doublons, rôle « co-éditeur », instrumentation des métriques. Plus deux parcours que la doc décrit et que le proto **n'ouvre volontairement pas** (tranché à l'audit du 2026-09-10) :

## 12. Navigation shell

### `/` ([`screens/dashboard.js`](../../src/screens/dashboard.js)) — un redirect, et rien d'autre

**Un redirect pur** : first-time sans Playbook → `/welcome-alt` ; sinon → la session la plus récente **dans le scope** (`scopeSessions`), ou `/session/new`. C'est le bon défaut pour un outil qu'on ouvre avec une tâche déjà en tête, et c'est le seul comportement de cette route.

⚠️ La front page magazine du flag `frontPage` (remplie par le listening) est partie avec le magazine Topics (§17). Si une front page revient, elle revient **sur la donnée du Topic Feed**, pas comme second lecteur d'un second store.

### `/home` ([`screens/home.js`](../../src/screens/home.js) + [`home/hero.js`](../../src/screens/home/hero.js), [`home/lists.js`](../../src/screens/home/lists.js)) — la home du **compte** (flag `playbookWorkspace`)

Là où `/` est la maison de la **marque** active (un redirect), celle-ci est la maison du **compte** : le niveau au-dessus des workspaces, atteint en cliquant le wordmark de la rail. Account scope — pas de rail, topbar réduite à « ‹ Back to <marque> » ([`ROUTES.md`](ROUTES.md) § Deux niveaux de chrome).

⚠️ **Ce n'est pas le retour de la front page** supprimée avec le magazine (§17) : celle-là était une page de ce qu'Archie **propose**, remplie par le listening, montée sur `/`. Celle-ci est une page de ce qu'on **possède** — ses Playbooks et ses chats. Aucun `topics-store` lu, aucun Topic rendu, et `/` reste un pur redirect.

**Le héro** — `h1` « What do you want to work on? » + « Pick a Playbook, tell me what you need, and I'll open a chat on it. » + une carte portant une textarea, un menu **Add**, le **picker de Playbook** (même `.ap-select` que le switcher de la rail, moins son footer) et **Send** orange. `Enter` envoie, `Shift+Enter` retourne à la ligne, Send est `disabled` tant que le champ est vide — **sans légende de clavier sous la carte** : celle du chat (§1) porte en plus le drop de fichier, que rien d'autre n'annonce là-bas ; ici elle ne restituait que la convention par défaut d'un composer, et elle s'intercalait entre la carte et les workflows, qui sont le second geste de la même phrase. **Choisir une marque ne déplace pas le scope** — seul Send le fait, c'est le commit explicite. **Aucun héro quand il n'y a aucun Playbook** : un composer mort au-dessus d'un picker vide est exactement le champ grisé que les six pickers in-flow ont valu d'être supprimés ; l'empty state de l'onglet porte le seul geste utile.

**Le menu Add** offre exactement ce que celui du composer offre — PDF, vidéo, URL, texte collé, top posts, un Topic, une source connectée — mais **il ne fait aucun intake** : uploads, traitement et rejeu sont par session, et cette page n'en a pas. Il **lance** : l'item bascule sur la marque choisie, crée le chat et fait voyager l'intention dans **un seul** handoff, `pendingHomeAdd`, que `session.js` dispatche vers les **mêmes fonctions** que le menu du composer appelle (`startTopPostsInline`, `startTopicPickerInline`, `openAddSourceModal`, `startPillFromKind`, `askConnector`). Trois flows, trois clés, auraient été trois lignes de la table des handoffs disant toutes « la home a demandé ». **À plat, sections + divider** : l'ADS n'a pas de dropdown imbriqué, donc le flyout « Connected sources ▸ » du composer n'est pas reproduit — les sources connectées sont une troisième section titrée. « Browse connectors » est l'exception qui ne crée pas de chat : une galerie est une page. Ce qui est déjà tapé **part avec** (les deux handoffs), sinon reprendre Add effacerait ce que le lecteur venait d'écrire.

**Envoyer** = `setActivePlaybook` → handoff `pendingHomePrompt` → `/session/new-<ts>?contextId=…&title=<phrase tronquée>` → `sendMessage` à l'arrivée. Le Playbook et le nom voyagent dans l'URL (convention d'`objective-flow`), seul le texte a besoin d'un pont, et le handoff est à usage unique — recharger l'URL ne re-poste rien.

**Les trois workflows** — les mêmes cartes que le héro du chat neuf, depuis le **même renderer** ([`components/starter-card.js`](../../src/components/starter-card.js), extrait de `session.js` pour ça : un objet rendu à deux endroits a un renderer et des hooks `data-*` que chaque hôte câble, comme `topic-card.js`). Elles sont ici pour la raison qu'elles sont dans le héro : le composer répond à « je sais ce que je veux dire », celles-ci à « j'ai une source / une vidéo / un post gagnant et je veux un batch » — et sur la home on choisit en plus la marque où ça atterrit. Seul le dispatch diffère : le chat lance le flow sur place, la home bascule de marque puis crée la session dont le flow a besoin (`pendingStartBatch` / `pendingStartClipStudio` pour les studios, qui lisent déjà `playbookForNewWork()` en démarrant ; `pendingHomeAdd` avec le kind `top-posts-studio` pour le board, qui vit dans un chat). Pleine largeur, contrairement à la colonne de 720px du héro, pour partager ses bords avec le tableau en dessous. **24px sous le composer**, le seul écart de la page : ni padding bas sur le héro, ni marge haute sur les workflows, ni légende entre les deux — les deux moitiés d'un même geste (« dis-le, ou pars d'une de ces trois »), même règle que la barre d'onglets où un calage à la main avait déséquilibré la bande.

**Deux onglets** DS (`.ap-tabs`), **tous les deux en `.ap-table`** (§9 pour le pourquoi), état dans l'URL (`?tab=chats|playbooks`) pour que le Back du navigateur passe de l'une à l'autre. **Chats est le premier et le défaut** : le sujet de la home est le travail ; le catalogue est ce qu'on ouvre pour basculer, créer ou gérer.

- **Chats** — **tous les chats, toutes marques** (`getSessions()` non scopé) en `.ap-table` : Chat · **Sources · Ideas · Drafts** · Playbook · Last activity. Les trois nombres disent jusqu'où le travail est allé (`getSources` / `getIdeas` / `getPosts`, par session) et ont **chacun leur en-tête de colonne** plutôt que trois icônes dans une cellule : un nombre a besoin de son nom en texte, et dans un tableau l'en-tête EST ce nom. Un zéro s'affiche, en gris atténué — une cellule vide dans une colonne de nombres se lit « inconnu », alors que « ce chat n'a rien produit » est un fait utile. ⚠️ Ce n'est pas l'inverse de la décision prise §9 sur l'onglet Playbooks, qui vient de PERDRE ses compteurs : personne ne choisit une marque au nombre d'audiences de sa fiche, mais « 3 sources · 5 idées · 2 drafts » est exactement ce qu'on cherche dans une liste de travail. La marque est **nommée en texte** (dot + nom), grise et « No Playbook » si la fiche est inaccessible. **Ordre : la récence, rien d'autre** — plus d'épinglés en tête ni de glyphe d'épingle : épingler est un geste qu'on fait à un chat DANS son workspace, donc la rail est où ça se trie et où ça se voit ; ici la seule colonne d'ordre visible est Last activity, et une liste triée sur un fait qu'elle n'affiche pas se lit comme arbitraire. Un clic **re-scope** — `setActivePlaybook` puis on ouvre — sinon le lecteur atterrit sur un chat que la rail à côté ne liste pas. Un chat sans Playbook s'ouvre sans toucher au scope : il vit partout par construction.

- **Playbooks** — le catalogue (§9) : chaque carte est une porte vers son workspace (bascule + chat neuf), le crayon garde la fiche.

La recherche est unique et filtre l'onglet actif — sur les chats, le nom **et** la marque, parce qu'une colonne visible doit être cherchable.

Les chevrons racontent le pipeline.

Puis une section par objet, séparées par un filet (jamais encartées) : **Sources** (tuile de type, nom, « 2 ideas, 5 clips » → la source focalisée) · **Ideas** (« 3 of 5 drafted » + une courte jauge ; les 3 premières, non draftées d'abord, avec leur tag de kind) · **Clips** (une pellicule défilante de leurs vignettes, avec la durée) · **Drafts** (des extraits de posts : logo réseau, 2 lignes, statut Ready / Needs fixes, vignette média). Chaque section nomme ses chiffres en mots quand ils disent autre chose que son titre (Sources et Clips n'en ont pas : l'onglet porte déjà le compte) et mène à son onglet par un seul verbe, _Open_, ou _See all N_ quand la liste est tronquée ; une section vide dit comment en avoir.

Dans le panneau, la vignette d'un clip plafonne à 200px de haut (PN-21). Le rail d'un draft garde ses boutons gris, sauf **Schedule**, stroked bleu (PN2-07). L'onglet ouvert porte « Select again to close the panel » en `aria-description`. Ideas : **ni sous-onglets ni filtre de kind** — Clips est un onglet de l'en-tête, les cartes viennent directement ; la carte perd son libellé « Source: », Why this idea devient une ligne discrète. Drafts : la bande de chaque réseau se fond dans le canevas.
- **Dans le fil**, chaque résultat est une carte qui ouvre le panneau **sur ses objets** (`focusManyInPanel(kind, ids, key)` : pulse de chacun, scroll sur le premier) et reste `.is-active` tant que le panneau est ouvert depuis elle (`getFocusKey()`) : lot de drafts (« 4 drafts to review » + réseaux — il n'avait pas de carte), lot d'ideas (remplace le notice dépliable), ideas ready, clips. L'écho d'une source est un bouton vers cette source ; ses liens « N ideas › » / « M clips › » focalisent les ideas / clips de cette source.
- **Pas d'annonce en double, pas d'auto-open** : ni toast « N drafts / ideas ready », ni barre verte du composer ; la carte du fil + le point sur l'onglet suffisent. Le panneau ne s'ouvre jamais tout seul.

## 17. Topic Feed — la file du listening

Le seul endroit où **Archie propose** au lieu d'attendre. Le listening Agorapulse remonte des posts sociaux sur huit sources rattachées à un Playbook ; Archie en assemble un **Topic** : une accroche (le constat), une analyse écrite en deux sections, et les posts qui la fondent. `/topics` est la **file où on la trie**. Toujours là : l'ancien flag `topicFeed` a été baké ON le 2026-10-07. Les critères d'acceptation : [`specs/AC-TOPIC-FEED.md`](../specs/AC-TOPIC-FEED.md).

Porté depuis le fork `axel-van/rebel-racoon` (@ `dbfd9d3c`), avec les corrections de l'audit UX signalées ci-dessous. Fichiers : [`topics-catalog.js`](../../src/topics-catalog.js), [`topic-feeds-store.js`](../../src/topic-feeds-store.js), [`topics-store.js`](../../src/topics-store.js), [`topic-article.js`](../../src/topic-article.js), [`topic-flow.js`](../../src/topic-flow.js), [`screens/topics.js`](../../src/screens/topics.js), [`screens/topics-settings.js`](../../src/screens/topics-settings.js), [`components/topic-card.js`](../../src/components/topic-card.js), [`components/topic-picker-modal.js`](../../src/components/topic-picker-modal.js), [`components/topic-history-modal.js`](../../src/components/topic-history-modal.js), [`components/topic-ignore-modal.js`](../../src/components/topic-ignore-modal.js), [`components/social-post-card.js`](../../src/components/social-post-card.js) ; le hero d'un chat neuf dans [`screens/session/empty-hero.js`](../../src/screens/session/empty-hero.js).

### ⚠️ Ce qui a été supprimé pour faire place

Le proto portait un **magazine** Topics : une une + une grille, transverse à tous les Playbooks, `ctx.topics` sur le Context, une front page sur `/` (flag `frontPage`), un rail de trois accroches dans le hero, deux verbes (Start a chat / Dismiss). **Tout est parti** — modules, feuilles, les flags `topics` et `frontPage`, la ligne de nav Home. Ne pas le ramener. C'est ce qui a libéré les noms canoniques (`/topics`, `topics-store.js`, `topic-card.js`, `topic-flow.js`) — au lieu du vocabulaire `research` / `lane` / `brief` que le fork gardait dans son code.

### L'invariant dont tout dépend

> Le **statut de revue** d'un Topic et ses **deux signaux d'attention** sont trois choses séparées.

`status` (`new` / `used` / `ignored`), `isTrending` et `isUpdated` sont trois champs (plus `kind`, ci-dessous). Ni signal n'est un statut, donc un Topic peut être **Used et trending** à la fois — et un signal ne **prime jamais** sur le filtre : un Topic ignoré qui se met à monter reste caché. Cocher **Ignored** dans le filtre est le seul chemin de retour. ⚠️ La règle inverse — « une pointe n'est jamais masquée par le triage » — a été essayée et retirée : elle faisait d'Ignore une suggestion au lieu d'une réponse.

Le **triage vit dans sa propre map**, pas sur le Topic : un Topic est ce que le scan a rendu, une ligne de triage est ce que **cet** utilisateur en a fait — un re-scan peut remplacer un Topic sans écraser la réponse. `topicStates(topic)` dérive les quatre champs en une liste plate pour l'affichage ; les fusionner laisserait un fait masquer l'autre (et le contrat de tracking `AC-TRK-6`, qui les reporte indépendamment, tomberait).

### Les deux stores

**`topic-feeds-store.js`** — un **feed par Playbook** : quelles sources écoutent, à quelle cadence, et quels sites la source Brand website lit. Global, comme `connectors-store`. **Pourquoi pas un champ du Playbook** (le magazine gardait `ctx.topics`) : un Playbook est une **fiche** ([`CONCEPTS.md`](CONCEPTS.md) §1), « quels feeds tournent et à quelle fréquence » est opérationnel. Ça achète aussi `websites` : la liste de scan d'**un** feed (un blog, un site de docs…), distincte du `websiteUrl` canonique du Playbook.

**Tout Playbook a un feed, et il écoute dès le premier jour** : `provisionMissingFeeds()` en crée un à la lecture, jamais au chargement du module (en `new-alt` les Playbooks arrivent plus tard). Rien ne peut **supprimer** un feed : la lecture suivante le reconstruirait.

**`topics-store.js`** — les Topics + le triage : `getTopicsForFeed` · `groupTopicsByAge` · `countToReview` · `countFresh` · `getFreshTopics` · `getPickableTopics` · `getTopicById` · `topicTitle` · `topicStates` · `defaultFilters` / `narrowedGroupCount` · `markUsed` / `ignoreTopic` / `unignoreTopic`.

**Un signal ne vit que dans « Last 7 days ».** Trending et Updated sont des affirmations sur **maintenant** : `withTriage()` les efface au-delà du premier groupe d'âge. Chaque lecture passe par cette fonction, donc le feed, le picker, le hero et tous les compteurs sont d'accord, et aucun seed ne peut réintroduire la contradiction.

### La file (`/topics`, [`screens/topics.js`](../../src/screens/topics.js))

**Un Playbook à la fois.** Flag `playbookWorkspace` OFF : porté par `?pb=` (le défaut sinon), qui survit à un lien et **s'arrête à cet écran** ; la page de réglages lit le même param, donc le scope survit à l'aller-retour. ⚠️ Le fork re-scopait toute l'app (compteur de la sidebar, Playbook d'un chat neuf, picker du composer) depuis un select qui ressemblait à un filtre de page. Flag ON : la rail porte le scope, `?pb=` n'est plus lu ni écrit, le select Playbook de la toolbar disparaît, et sur la page de réglages « Open Playbook » devient « Open <marque> ».

**La rangée de page** : sous la phrase de concept (`conceptText("topicFeed")`), **une toolbar** — le select `Playbook │ …` (DS Select en `<details>`, label en `.ap-select-inline-label`) puis **Filters**, libellé avec son compteur. Le **cog** des réglages est à l'extrême droite de la **topbar** ([`topbar.js`](../../src/components/topbar.js)), qui imprime aussi le nom de la route : le document n'a qu'un `<h1>`. ⚠️ Écartés : une rangée de titre dessinée (« Topic Feed » deux fois), la fusion toolbar + onglets en une rangée, et le compteur « N topics » au-dessus de la liste (retiré).

#### La page est un LECTEUR

Une liste à gauche, un volet de lecture à droite, **les deux colonnes défilent indépendamment**.

- **Le cadre appartient aux OBJETS** : chaque Topic est une carte, le volet est une carte à part, la rangée ne fait que les espacer. ⚠️ Un cadre unique autour de la rangée a été essayé contre l'effet « mur de cartes » : le mur venait des gaps et du poids, pas des bords. Si une liste pèse trop : resserrer les gaps, alléger la graisse, clamper — pas déshabiller les items.
- **Largeur : calculée en CSS, alignée à gauche.** `--topic-measure` (600px) et `--topic-list-max` (460px) sur `:root` dans [`styles/screens/topics.css`](../../styles/screens/topics.css) ; le cap vaut `list-max + gap + measure + 2× padding du volet` (1132px), le volet `measure + 2× padding`, la liste le reste. Le reste va dans la marge de **droite** : les rangées démarrent au bord où la topbar pose son titre. ⚠️ Centré, rien ne partageait de bord avec le chrome ; et un cap écrit à la main (1440) dérivait de la mesure — un cap sur une surface de lecture se **dérive** de ce qu'elle contient.
- **Le volet est la moitié FIXE, la liste celle qui s'étire** (`flex: 0 1 calc(measure + 2× padding)` contre `flex: 1 1 0`) : une fenêtre plus étroite rabiote la file, jamais la prose. Plancher de la liste : 340px. (La base doit être `0` : sur `auto` la liste écrase le volet.)
- **Le volet épouse la hauteur de son article** (`align-self: flex-start` + `max-height: 100%`, `pane-body` scrolle) ; seul le volet **vide** garde `stretch`, pour tenir la colonne ouverte.
- **Le bord du volet rencontre celui des cartes** : le volet est inset de la boîte du séparateur d'âge, `--topic-group-offset` (line-height du label + son écart). ⛔️ Le séparateur doit rester **la seule chose** entre le haut du scrollport et son premier groupe : tout nouvel élément au-dessus des groupes sort du split, ou ajoute son terme au token.
- **Une seule `@container` query** (760px, conteneur `.topics-view__body`), pas une media query : la sidebar se replie et le panneau de droite recouvre. En dessous, le split s'empile, le scroll revient à `.topics-view` (`overflow-y: auto` **inconditionnel** — une container query ne style que les descendants de son conteneur) et ouvrir un article fait défiler jusqu'à lui (arithmétique, pas `scrollIntoView()`).
- **La position de scroll survit à toute action** : `paint()` restaure les offsets autour du repaint.

#### Rien d'ouvert, et rien du tout

Le volet **rend un placeholder** plutôt que de disparaître, pour que la liste ne saute pas. Quand il n'y a **rien à lire du tout** — feed vide, filtre qui exclut tout — l'état prend **tout le lecteur**. **L'attente garde le split en fantômes** : cinq cartes-fantômes et un article-fantôme dans les vrais cadres, la ligne de statut au créneau du séparateur d'âge. ⚠️ C'était un `.ap-loader` seul au centre, suivi d'un lecteur qui apparaissait autour.

#### ⚠️ Vu / non vu : remis à plus tard

Un axe `seen` (accusé de lecture, compteur de non-vus, `Mark all as seen`) a été construit puis **retiré** ; `git log -S countUnseen` le rend. Il reste le fond `grey-05` d'une carte `.is-triaged`. S'il revient : `status` dit ce qu'on a **décidé**, `seen` dirait si on a **regardé** — l'un des deux doit être clairement subordonné.

#### Les six états, à un seul niveau

**Le DS TAG** (`.ap-tag <tone>` + `> i` + `> span`), tons et icônes déclarés dans le catalogue. ⚠️ C'étaient des `.ap-status no-dot` (Status n'a pas de créneau d'icône), avant cela deux `<span>` faits main ; et For later était un onglet, Used / Ignored des icônes nues. Une pastille par état, zéro CSS maison (`--comp-tag-*`).

| État         | Teinte Tag  | Icône                   | Pastille |
| ------------ | ----------- | ----------------------- | -------- |
| To review    | —           | —                       | **non**  |
| Trending     | `tagOrange` | `ap-icon-arrow-up`      | oui      |
| Updated      | `menthol`   | `ap-icon-refresh`       | oui      |
| Already used | `green`     | `ap-icon-rounded-check` | oui      |

#### Les filtres

Le **DS Filter dropdown** (`.ap-filter-dropdown`, porté dans `ds-patches.css`), **trois groupes**, chacun un `.ap-select` multi-sélection :

- **Topics** — sur `kind`, **vide au repos** : To review et For later dans une seule liste ; cocher une voie rétrécit à elle.
- **Marked as** — les statuts **répondus** (Already used / Ignored), ajoutés par-dessus la base To review (`new` n'est pas une ligne). **Already used coché au repos, Ignored non.**
- **Sources** — les live cochables, les six autres désactivées avec un `.ap-tag grey mini` « Coming soon ».
- ⚠️ **Trending et Updated ne sont PAS des lignes de filtre** : le prédicat (`matchesFilters`) ne lit jamais un signal, donc aucun ne peut remonter un Topic ignoré (`AC-PICK-2b` / `AC-SIG-2` par construction).
- La sélection s'affiche **en chips dans le trigger** (la pastille de l'état pour Marked as, le badge de la source pour Sources — jamais un chip bleu).
- L'ouverture des selects est dans `view` (`kindOpen` / `markedOpen` / `sourcesOpen`), pas laissée à `<details>` : cocher repeint le panneau. Un seul ouvert à la fois ; Escape ferme le select ouvert, puis le panneau, puis le volet. Le contenu du panneau est en `overflow: visible` pour que le menu du bas ne soit pas rogné.
- **Le badge compte les GROUPES rétrécis** par rapport au défaut (`narrowedGroupCount`) — rien au repos. **Reset filters** restaure les défauts.

#### Groupes d'âge, pagination

Trois groupes, dans cet ordre : **Last 7 days** (≤ 7j) / **Earlier this month** (≤ 30j) / **Earlier**, groupes vides masqués, définis dans le store. `ageLabel` (« 2d ago ») est **la seule entrée d'âge** : la carte et le groupe en dérivent ; `topics-store.ageMinutes` est la couture à remplacer par de vrais horodatages. **Dix par page** : une sentinelle charge la suivante, et un **Load more** explicite fait la même chose (une liste infinie sans bouton est inutilisable au clavier) ; `loadingMore` empêche un double chargement.

#### Les cartes ([`topic-card.js`](../../src/components/topic-card.js))

Deux variantes, toutes deux des cartes : `--feed` (peut être **celle qui est ouverte** et raffermit sa bordure) et `--picker` (le hero d'un chat neuf), plus la rangée radio du widget in-chat. La règle de base ne porte **aucun** cadre : chaque cadre vit sur une variante. Le feed et le hero sortent **la même carte, partie pour partie**.

- **L'ordre : la ligne meta d'abord** (`badge · source · âge · puces`), puis l'accroche, puis le résumé ; l'article du volet s'y range (`AC-TITLE-2`). ⚠️ L'accroche en tête a été construite d'abord et recalée pour la carte et le volet (seule la dialog, plus large, met le titre en premier : `titleFirst`).
- Les puces d'état viennent de `topic-article.js` (`renderTopicStates`), pour que la carte et l'article disent la même chose (`AC-TITLE-3`). **`new` ne rend rien** ; le signal part au bout de la ligne meta.
- **La carte est une surface de lecture** : le corps est **un seul bouton** qui ouvre l'article ; le kebab est son **frère** (Use in chat, puis Ignore **ou** Un-ignore). Les verbes vivent dans l'article.
- **Non-triée en gras, triée en poids normal** — l'idiome lu/non-lu d'un client mail ; l'encre ne change pas.
- **Hover et sélection** : au survol un lavis + bordure bleu clair, jamais d'élévation ; la carte ouverte **raffermit** sa bordure en `electric-blue-100`. ⛔️ **Jamais** de bordure gauche colorée sur la carte ouverte.
- Les intertitres d'âge sont de simples libellés au-dessus de chaque groupe (plus de bandeau collant).

#### L'article — un seul moteur, trois hôtes ([`topic-article.js`](../../src/topic-article.js))

Le volet du feed, la dialog de l'article ([`topic-picker-modal.js`](../../src/components/topic-picker-modal.js), ouverte depuis le hero d'un chat neuf) et sa vue historique appellent **les mêmes fonctions pures** (`renderTopicHeader` · `renderTopicArticle` · `renderTopicPosts` · `renderTopicActions` · `renderTopicMenu` · `renderTopicTrail` · `renderTopicStates`) ; seul le placement appartient à l'hôte.

- **Contenu** : le titre (**le titre de l'article**, `topicTitle()` ne prend l'accroche qu'en repli), la provenance et les puces, au plus deux faits (**Relevance** / **Why now**), la prose dans ses deux sections, puis les **Contributing posts** (« pas Sources » : une Source est ce qu'on amène dans un chat). Pas d'historique de version.
- **Le volet** : l'en-tête (provenance, titre, kebab en haut à droite) **hors du scroller**, à hauteur fixe ; **pas de Close** (un lecteur à deux volets ouvre le suivant ; Escape ferme). Les deux verbes sont **au pied de la lecture**, sur une barre collante (`.topic-article__actionbar`) entre l'analyse et la preuve, qui porte aussi la bascule « Contributing posts N » : le lecteur décide en ayant fini de lire. Le kebab tient **Topic history** (le nombre d'entrées en description), ouvert dans [`topic-history-modal.js`](../../src/components/topic-history-modal.js). ⚠️ Une barre de verbes seule au-dessus d'un titre qui défilait, puis la trace en dernière bande de l'article (dans un accordéon), ont été retirées.
- **La dialog** : titre en premier, deux colonnes — l'identité et l'analyse à gauche, les Contributing posts **dépliés** dans un panneau gris pleine hauteur à droite — et un `.ap-dialog-footer` : **History** à gauche (bascule le corps sur la trace, « Back to Topic »), **Ignore** · **Use in chat** à droite ; le × en haut à droite. ⚠️ La dialog ne peut pas ouvrir la modale d'historique (elle est l'overlay actif, `requestOpen` la fermerait). La modale d'historique consomme Escape **en capture** (`stopPropagation()`), sinon le handler Escape du feed fermait aussi l'article.
- **Relevance et Why now sont la première bande**, dans le scroller : deux blocs **pêche** (`--ref-color-orange-10`, glyphe en `orange-150`), le label **au-dessus** de sa phrase. ⚠️ Dans l'en-tête fixe, ils faisaient varier sa hauteur d'un Topic à l'autre (125 → 291px) ; une colonne de labels créait un second bord de texte. **Jamais teintés par un signal**, jamais tronqués.
- **Deux fonds, distingués par la teinte** : pêche = la lecture d'Archie (les faits), gris (`--app-surface-subtle`) = les mots de quelqu'un d'autre (les posts cités). ⚠️ Cela **élargit** la règle de l'orange à « la voix propre d'Archie » — décision assumée, **pas une licence** pour teinter d'autres données statiques en orange. Pas de bordure ni d'ombre sur ces blocs.
- **Un Topic `later` a son analyse** : un encart en tête, « Not enough to draft from yet » (le thème vaut d'être gardé, il n'y a pas assez autour pour un draft), **au-dessus** de la prose, jamais à sa place. ⚠️ Le corps a longtemps remplacé l'analyse par un placeholder alors que les 18 Topics `later` en portent une.
- **Les Contributing posts sont repliés au repos**, toujours, quel que soit le `kind` ; le compteur annonce le total, et l'ouvrir montre **tous** les posts (plus de plafond « N more posts »). Le dépli est une **checkbox voisine** (le renderer est pur, sans état d'ouverture), pas `<details>` ni `.ap-accordion`.
- **La carte de preuve est celle du produit** ([`social-post-card.js`](../../src/components/social-post-card.js), modelée sur `ap-mini-post`) : top (avatar 40px avec le réseau en **badge** `.ap-avatar-network` · `@handle` · nom · date), content, bottom (l'engagement, **compteurs à zéro omis**) ; blanc sur filet grey-10, pas de hover. Non portés faute de données : le sentiment et le surlignage des mots-clés.
- **L'échelle est 24 / 16 / 14 / 12** — le titre en taille `h1` sur un élément `<h2>`, les sous-titres d'analyse en `h3`, la prose en `body`, l'appareil en `caption-bold` light ; « Contributing posts » en `body-bold` (c'est une porte), hover bleu électrique. Cinq pas d'espace : 2 (label → phrase), 8, 12 (paragraphes et posts cités), 28 (au-dessus d'un sous-titre), 32 (entre bandes). ⚠️ Les règles `__body`, `__para`, `__subhead`, `__section`, `__section-head`, `__posts` ont été supprimées une fois par accident (`15284825`) : rien n'y est décoratif.

#### Les deux verbes

Dans l'ordre secondaire → primaire : **Ignore** (`stroked grey`, pas rouge : rien n'est détruit), puis **Use in chat** (`primary orange` dans l'article, volet et dialog).

- **Use in chat** ([`topic-flow.js`](../../src/topic-flow.js)) — `useTopicInChat()` marque le Topic **Used** (avant que le chat s'ouvre, en un seul endroit), arme le handoff `pendingTopicChat` et navigue vers un chat neuf `?contextId=…&title=<titre>` (lié et nommé au premier paint). Au mount, `attachTopicToChat()` l'attache comme **source** : tout ce qu'une source sait faire (idées, draft, Ask, panneau Sources) s'allume sans cas particulier. - **Ignore** — [`topic-ignore-modal.js`](../../src/components/topic-ignore-modal.js) : « Why did this Topic miss the mark? », le titre cité, un champ **optionnel**, un infobox sur ce qu'ignorer implique. Le motif est conservé et réimprimé sur l'état Ignored. ⚠️ La case « Don't show this again » du fork est retirée (elle faisait d'Ignore un clic sans motif). Réversible : le toast offre **Undo** (`unignoreTopic`), qui repasse en `new` et **efface le motif**.

## 18. Image Generator — générateur d'images IA

Un **générateur d'images IA** pour les posts Instagram, Facebook, X et LinkedIn, code dans [`src/modules/image-studio/`](../../src/modules/image-studio/), préfixes `.imst-` / `data-imst-` / `imageStudio:`. Toujours là : l'ancien flag `sexySquirrel` a été baké ON le 2026-10-07 et l'ancien Image Studio (`src/image-studio.js`) supprimé avec lui. Le contrat d'intégration est dans [`audits/image-studio-integration.md`](../audits/image-studio-integration.md) ; le module n'importe d'Archie que le shell (router, flags, topbar) et, par [`state/playbook-brand.js`](../../src/modules/image-studio/state/playbook-brand.js) seulement, les Playbooks. **Il n'a pas de section à lui** : pas de ligne de nav, pas de History, pas de page d'éditeur (⚠️ la page `/image-generator/editor/:id` a été supprimée avec la section, le 2026-09-28). Il a **deux surfaces**, et deux seulement :

1. **Le studio, dans la dialog d'un draft** — le seul endroit où l'on choisit style, forme et texte (« Generate an image » sur un draft fait une image directement, sans lui).
2. **Les styles de la marque, dans l'onglet Image generation du Playbook** (§9) — et leur créateur, une page de la fiche.

- **La marque, c'est le Playbook.** Le générateur n'a pas de marques à lui : il lit le Playbook du chat — logos et leur version, couleurs et leur rôle, typo, images de réf., mots à éviter, règles visuelles, **styles** (le **kit de marque**, §9) — à travers **un seul** fichier, `state/playbook-brand.js`. Il n'écrit la fiche qu'en un cas : un style de la marque enregistré par le créateur. Pas de sous-marques : une déclinaison est un Playbook dupliqué ([`CONCEPTS.md`](CONCEPTS.md) §1). ⚠️ La ligne de marque du studio (logo, nom, pastilles, switch « Use the Playbook ») a été retirée le 2026-09-29 : une image faite depuis un draft est **toujours** celle du Playbook du chat. `unbranded()` ne sert plus qu'à redessiner une création enregistrée avec le switch éteint.

### « Generate an image » — une image, directement dans la fente

[`draft-image-flow.js`](../../src/draft-image-flow.js) : le clic lance **directement** le loader dans la fente du draft (`<archie-pixels>`, voir [`UI-PATTERNS.md`](UI-PATTERNS.md) § Le loader de génération d'image), qui narre ses étapes. Ce qui est utilisé, sans question — exactement ce que dit la légende sous le bouton : **le style** = le look par défaut du Playbook (Playbook › Image generation : un style ou une image de référence), sinon son premier style, sinon un preset ; **la forme** = la forme préférée du réseau ; **aucun texte** sur l'image ; **ce que montre l'image** est lu dans le post (« Suggest from the post », 4–8 s comme l'appel réel : la première étape du loader). Puis l'image arrive en place. **Aucun message dans le chat** ; un échec → le toast « Couldn't generate the image. » avec **Retry** ; chat sans Playbook → un toast. Mêmes services que le studio (`quick-image.js` : `quickImageChoices` / `suggestImageSubject` / `generateQuickImage`, exportés par `index.js`). **L'image rendue est une photo de stock** : `generateQuickImage` garde l'attente et les échecs du mock mais renvoie une photo Unsplash détaillée tirée de `MOCK.photos` (`config/mock.js`), recadrée à la forme ; le studio, lui, dessine ses rendus de style. ⚠️ Remplace le flow « posé en chat » (jusqu'à trois Quickpickers — style, forme, texte — puis « What next? », retiré le 2026-10-08) : ne pas le reproposer. Pour choisir le style, la forme ou le texte : le studio (bouton **Image Studio** à côté, ou Edit sur l'image).

**La première image — le look demandé UNE fois** (`requireImageLook`) : quand le Playbook du chat **n'a pas de look** (`needsImageLook` : pas de `defaultLook`, et il est modifiable par l'utilisateur), le premier clic ne lance pas le loader : je demande dans le chat — (1) « First image for {Brand}. How should its images look? … » : **From images I already have** / **A ready-made style** (Quickpicker ; **Not now** = l'image est faite quand même dans le premier preset, et rien n'est redemandé jusqu'au reload) ; (2a) les styles **en images** (ceux du Playbook en tête — s'il en a déjà, (1) saute) ou (2b) une dropzone « 2 to 6 » images → un **style de marque** « {Brand} look » enregistré sur le Playbook (`styleFromImages` = le save du créateur, sans sa page). Le choix **devient le `defaultLook`** aussitôt, un écho de sélection, un reçu « Done. {Brand}'s images start from **X** now. Change it any time in {Playbook}. **Undo** » (variant `image-look-set`, qui relit le Playbook), puis l'image arrive dans la fente — le flow reprend où il était (le pattern de `requireConnectedProfiles`). Playbook partagé non modifiable → pas de question. ⚠️ Ce n'est **pas** le flow « posé en chat » revenu : deux questions une seule fois par Playbook, jamais la forme ni le texte. **Les autres entrées** : la légende sous le bouton dit « First, I'll ask how {Brand}'s images should look. » ; sous le **dernier lot de drafts** du chat, tant qu'il n'y a pas de look, « Want an image on these? … **Pick a look** » (dérivée au rendu du turn `draft`) lance le premier Generate sur le premier draft du lot ; Playbook › Image generation › Generate an image, sans look : **Help me pick in a chat** (handoff `pendingImageLookChat` → un nouveau chat « Image look » sur ce Playbook, ouvert sur les mêmes questions) ; le recap de création, onglet Branding : **How your images look**, les six presets (optionnel, re-cliquer décoche) écrits dans le `defaultLook`.

### Le studio — la dialog d'un draft

Le bouton **Image Studio** d'un draft (ou Edit sur son image) ouvre le studio (`views/studio.js`, monté par `openDraftStudio`) dans une dialog titrée **« Image Studio »** — le nom de l'outil seul, sans citer le post.

- **« How do you want to start? » — le premier écran** : la dialog s'ouvre **sur ce choix seul**, avant tout contrôle, sur la surface du canevas ; le footer n'a que Cancel. Trois cartes, chacune montre ce qu'elle fait avant de le dire, puis une ligne « Good for… » :
  - **A style** : les styles de la marque en éventail, et leur nombre en tag (« 1 Acme style », sinon « 6 ready-made styles ») ;
  - **An image** : une image de référence qui passe son look à une autre ;
  - **From scratch** : une phrase en train de s'écrire.
  - Au survol, chaque image joue sa réponse (l'éventail s'ouvre, la référence passe son look, la phrase monte). Sur un écran étroit (≤ 1100px), les cartes s'empilent couchées. ### Edit — l'image en calques

On entre dans Edit par **Edit** sur l'image (barre du résultat) ou, si le draft a déjà une image, par **Edit the current image** sous l'écran de choix ; on en sort par **Back to the variations** (stroked blue) au-dessus de l'éditeur, à côté de « Editing variation 2 of 4 ». ⚠️ **Plus d'onglets Generate | Edit** dans l'en-tête (retirés le 2026-10-02) ni de **Refine** dans Generate : son champ est devenu le composer d'Edit (« Describe a change… » → **Redraw**). Edit s'ouvre sur **la variation choisie**, ou sur **la photo du draft** si rien n'a été généré. Il reprend l'Edit de l'ancien Image Studio — même markup, mêmes classes `.image-studio__*` / `.isv2-*`, donc ses deux feuilles, gardées (`image-studio-canvas.css`, `image-studio-v2.css`) : la palette à gauche (Crop · Add text · Add image, et sa feuille : marques du Playbook, Upload, les 16 tampons), le texte éditable sur l'image avec sa mini-toolbar (couleur, police, bold, italic, outline, shadow), la boîte de crop et sa toolbar dessous (« Best for », Freeform + **les formes du réseau du draft**, ✕ / ✓), le composer → Redraw, Image / In feed au-dessus, Undo à gauche du footer. Le code est au module (`views/edit/`).

- **L'image est une pile de calques** (`state/edit-doc.js`) — **Background** (toujours en bas, jamais déplacé, recadré avec le cadre ; « Image » pour la photo du draft, qui n'a qu'un calque), **Subject**, le **titre** s'il y en a un, le **Logo**, puis tout ce qu'on ajoute. Le sujet est **détaché du fond** au rendu (`render/split.js`) : les générateurs marquent tout ce qui lui appartient (`data-imst-part`, `render/generators.js`), et le même SVG est lu deux fois — sans le sujet, puis le sujet seul, recadré à sa boîte. Un style sans sujet (Big number, Quote…) n'a pas de calque Subject. Le titre et le logo arrivent **là où le générateur les avait mis**.
- **Le panneau Layers**, sur le bord droit (symétrique à la palette) : calque du haut en premier ; une ligne sélectionne, l'œil masque, le cadenas verrouille, ↑ / ↓ / corbeille sur le calque choisi. Le fond ne se verrouille ni ne se supprime — il se masque (un damier dit la transparence).
- **Redraw ne redessine qu'un calque** : le sujet ou le fond sélectionné, sinon les deux ; **jamais le texte ni le logo**. Nouvelle seed pour la partie visée, même découpe. Sur la photo du draft, Redraw est désactivé et le dit (« I can only redraw the layers I generated… »).
- **Chaque changement est un pas d'Undo** (⌘Z aussi). Clavier : Suppr efface, flèches (+ Shift) déplacent, Entrée édite un texte, ↑ / ↓ parcourent la liste, **Échap défait d'abord** (popover → crop → saisie → sélection) avant de fermer la dialog.
- **Les éditions collent à leur image** : un document par variation, gardé tant que la dialog est ouverte. De retour dans Generate, la variation éditée s'affiche éditée (tag « Edited »), et Use in draft / In feed prennent cette version-là.
- Un seul écart à l'ancien Edit : **seul le calque sélectionné** sort du cadre (l'ancien décadrait toute la couche d'overlays, et un sujet qui couvre l'image débordait partout).

### Carrousels (parité prod `generateCarousel`)

Un contrôle **Slides** (`.ap-select` DS, « 1 image » … « 10 slides ») sous Variations — config de RUN sur le brief, jamais sur le Playbook ; ouvert depuis un draft carrousel, il part du nombre de slides du draft. **Un run = une création**, un seul `styleSnapshot` (la « Style Bible » que partagent les slides) ; chaque variation porte `slides[]` — une seed et **une ligne du post par slide** (`copyService.slideLinesFromPost` : la slide 1 prend le texte sur l'image s'il y en a un), le même fond d'une slide à l'autre. Variations s'applique **par carrousel** (2 variations × 5 slides = 2 carrousels). Pendant la génération, « **Rendering slide N of M** » (`onProgress` ; la slide 1 prend l'attente pleine, les suivantes 0,7 s). ### Le modèle d'un objectif

**Un objectif est une intention qualitative — un label, pas une mesure.** Ce qui se mesure, c'est la **mesure** qu'il porte. Rien n'est stocké à part : `ctx.objective` reste un `string[]` sur le Playbook, l'identité d'un objectif est son **label**, et les corrections de l'utilisateur vivent dans `ctx.objectiveMeasures[label]` :

```
{ measures?: [ { id, metricId, scope?: { network, profileIds? }, baseline?, target?, window? } ],
  proxy?:   { metricId, baseline?, target? },       // objectif parqué
  window?:  { type: "rolling" | "fixed", date? },   // fenêtre de l'objectif
  grace?:   { day, of },                             // période de collecte
  origin?:  "user" }                                 // vs proposé par Archie
```

Un `measures` absent = les défauts du couplage. La liste se matérialise à la première correction structurelle (`materializeMeasureEntries`). Les anciens brouillons (maps par métrique `metricIds` / `baselines` / `targets` / `measureWindows`) sont normalisés à la lecture. `resolveObjectives(labels, contextId, overrides)` est le point d'entrée unique ; tout est **dérivé au rendu**.

**La clé d'un objectif** partout (modèle, mocks, handoff) : `` `${ctxId}::${label}` ``.

#### Le catalogue de métriques ([`objective-measures.js`](../../src/objective-measures.js))

18 métriques en 8 familles (Awareness, Audience growth, Engagement, Video, Reputation and care, Traffic, Paid, Conversion). Chaque métrique a un `type` :

- **volume** (Reach, Impressions, Video views, Paid reach, Profile visits…) ;
- **rate** (Engagement rate, Completion rate, Sentiment score, Response time) — sans échelle : jamais divisé par nombre de profils, la cible se lit « hold above X » ;
- **counter** (Brand mentions, Followers net growth, Comments, Saves & shares, Reviews, Link clicks, Demo sign-ups) — seuls les counters sont `additive`, et c'est **la seule chose qui débloque le scope « Every connected profile »** (ex-« All networks ») à la création.

`lowerIsBetter` (Response time) supprime la jauge de progression. `available: false` (Attributed revenue, Attributed sign-ups) = métrique réelle que la plateforme ne sert pas encore : listée grisée « coming soon » avec son proxy (Link clicks).

#### Couplage label → mesures

- **Couplé** (`COUPLINGS`) : « Brand awareness » → Reach + Brand mentions, « Build personal brand » → Followers net growth + Engagement rate, « Traffic » → Link clicks, etc. Un label libre se résout par : `COUPLINGS` exact → `PARKED` exact (insensibles à la casse) → premier alias regex (`ALIASES`) → parqué générique.
- **Parqué** (`PARKED`) : une intention réelle qu'aucune métrique native ne mesure — Lead generation, Sales, Product adoption, App downloads, Net Promoter Score. **Jamais supprimée** : affichée avec un `soon` (« Attributed revenue needs a Google Analytics connection. ») et un **proxy avoué** (Link clicks, ou Sentiment pour NPS). Un label inconnu tombe en parqué générique avec Engagement rate pour proxy. À l'écran : l'infobox DS `warning` « Needs Google Analytics » + le `soon`, et un badge `proxy` sur la ligne de mesure.

#### Scope, baseline, cible, fenêtre

- **Scope** : `undefined` (tous les réseaux) · `{ network }` · `{ network, profileIds }`. **Un réseau à la fois** — cocher un profil d'un autre réseau _déplace_ la mesure. La même métrique peut apparaître deux fois avec deux scopes (Reach LinkedIn et Reach Instagram sont deux mesures) : l'identité d'une mesure est son `id`, pas sa métrique.
- **Baseline** : valeurs pré-formatées (un proto montre, il ne mesure pas) — défauts, surcouches par Playbook, splits par réseau ; un sous-ensemble de profils divise la valeur réseau au prorata (sauf les rates). Éditable.
- **Cible** : pour « tous réseaux », authored (`DEFAULT_TARGETS`, surcouches par Playbook) ; pour un scope réseau, **baseline × 1,15** arrondi (`proposeTarget`, règle du prototype plateforme). Reste **« Suggested »** tant que l'utilisateur ne l'a pas éditée.
- **Fenêtre** : `rolling` (30 derniers jours, défaut, sans légende) ou `fixed` (se termine à une date). Définie sur l'objectif, héritée par ses mesures, déviable par mesure (seulement quand l'objectif est `fixed`).

#### Pace, trend, état, verdict

- **Pace** (projection vers la cible, depuis `progressPct` = courant / cible, borné 0–100) : ≥ 80 → On pace / Ahead, ≥ 60 → On pace, sinon Behind. Un **rate n'a pas de pace**, il tient une barre : Holding / Below.
- **Trend** : direction sur la fenêtre, mockée par métrique et surchargée par Playbook (Acme : Reach −8 %). > +1 % Up, < −1 % Down, sinon Flat.
- **État d'une mesure** (`measureState`) : `on` / `soft` / `off`. Volume : Behind → off ; sinon trend Down → soft ; sinon on. Rate : Below → off si Down, soft sinon ; Holding + Down → soft.
- **Verdict d'un objectif** (`objectiveVerdict`) — **un COMPTE, jamais un score pondéré** : toutes les mesures `on` → **On track** ; aucune `on` et au moins une `off` → **Off track** ; le reste → **At risk**. Phrase : « 2 of 3 measures on track ». Un objectif parqué est jugé sur son proxy.
- **Collecting** : un objectif en période de grâce n'a **aucun verdict** (« Collecting data · day 4 of 7 »). Un objectif créé par l'utilisateur démarre à `{ day: 1, of: 7 }` ; le seul exemple seedé est `ctx-founder-voice::Thought leadership` (jour 4/7). Dans les layouts : pastille grise « Collecting », figure « N/7 days collected », overlay sur la courbe.
- **Présentation des paliers** ([`objective-scoring.js`](../../src/objective-scoring.js)) : `TIER_LABELS`, `TIER_STATUS_CLASS` (`green` / `tagOrange` / `red` — `tagOrange` et pas `orange`, réservé à l'IA), `TIER_ORDER`. Le moteur pondéré qui vivait là (`effectiveScore` / `playbookScore` / `objectiveTier`) est **supprimé** : deux moteurs d'accord « par construction », c'est un de trop.
- **Pas de verdict au niveau du Playbook.** `playbookRollup` compte les objectifs par palier (+ progression moyenne des objectifs mesurés, nombre de posts) ; son `worstTier` sert au tri, il n'est jamais rendu. À l'écran : `tierCounts`.

### Le modèle d'affichage ([`insights/model.js`](../../src/screens/insights/model.js))

**Un seul modèle pour tous les layouts** : `objectiveEntries(ctx)` rend une Entry par objectif, **triée pire d'abord** (palier puis progression) ; changer de layout ne peut donc jamais changer ce qui est dit. Le module ne tient **aucun état**.

Une Entry porte : `key`, verdict + palier (+ `collecting` / `parked`), `origin` (`archie` sauf `origin: "user"` → « Set by you » / « Proposed by Archie »), la fenêtre (avec `daysLeft` pour une fenêtre fixe), les mesures enrichies, la **mesure de tête** (`headline` = la plus faible : pire état, puis progression la plus basse), `nextMove`, les posts liés et des compteurs. `readingFor(entry)` en tire la phrase d'une ligne (« Reach is at 74% of target, down 8% this period. »).

- **Série par mesure, déterministe** : aucun `Math.random`. Extrémités = les vrais chiffres de la mesure (courant, trend, cible), intérieur = une table de bruit fixe indexée par un hash FNV-1a de la clé, fenêtre de 30 jours ancrée sur `TOP_POST_TODAY`. Deux paints d'un objectif tracent la même ligne. Une fenêtre fixe prolonge l'axe jusqu'à l'échéance (60 jours max) et trace la **Required pace** en pointillé ; la cible est une ligne pointillée.
- **Posts liés** : seuls les posts **draftés avec Archie** et publiés comptent. Authored dans `objectivePosts` (6 objectifs), sinon générés de façon déterministe depuis `objectivePostPool` (2 à 4 posts). Chaque post porte sa **contribution** (« +3,300 reach · 1.9× median ») et sa part de la mesure ; il apparaît sur la courbe comme un marqueur « Posts I drafted ». **Pas de retrait** : un post est là parce qu'Archie a mesuré qu'il a fait bouger l'objectif, le lecteur ne peut pas le « dé-observer » (l'ensemble de posts retirés et son notifier ont été supprimés).
- Rendu : la carte du board des winners (`renderTopPostCard`) en variante `--neutral` (le multiple en encre, pas en vert — le vert veut dire « on track » ici), stat strip contribution + « of the measure », CTA **Repurpose**.

### Les layouts — le View switch

Défaut : `cockpit`. ⚠️ C'est du **chrome de prototype**, pas de l'UI produit : les lectures sont gardées côte à côte pour être comparées en direct ; le jour où une gagne, les autres sont un delete (et `views.js`, `read.js`, `insights-read.css` avec elles).

| `cockpit`   | Cockpit     | Master–detail : un rail de tous les objectifs (anneau, nom, verdict — **pas de sparkline**), l'objectif sélectionné lu en entier à droite : phrase, readout (score + current + target), courbe avec **onglets DS par mesure**, table des mesures (Current / Target / Progress / Trend / Trajectory / State), grille des posts. Sélection = `?objective=`.           |

Règles tenues par le shell : un layout est un `render(host, vm) → cleanup` pur, sans listener ; toutes les actions sont des hooks `data-ins-*` dispatchés par le shell, lié **à `#app` et à `#topbar`** (le switch vit hors de `#app`). Changer de vue ne rejoue **pas** l'animation d'entrée ; elle ne joue qu'à une nouvelle lecture (clé de montage = id du Playbook actif). Les notifications de store sont coalescées en un paint (`setTimeout 0`, pas `rAF`, qui ne tire pas dans un onglet caché). ### Le scope : le Playbook actif

Insights lit `getActivePlaybook()` d'[`active-playbook.js`](../../src/active-playbook.js) **flag `playbookWorkspace` ou non** (persisté en `localStorage` `archie-active-playbook` ; repli sur le Playbook par défaut puis le premier). Le shell s'abonne à `contexts-store` et au scope.

- **Flag workspace OFF** : le nom du Playbook en tête de chaque layout **est le switcher** (`playbookTitle`, un `<details>` DS select sur `getContexts()` ; titre statique s'il y a moins de deux Playbooks). C'est la seule porte vers le scope dans l'app, donc chaque lecture le garde — y compris la page vide. Choisir un autre Playbook appelle `setActivePlaybook` et purge un `?objective=` de l'ancienne marque.
- **Flag workspace ON** : `playbookTitle` rend une chaîne vide — le switcher du rail nomme déjà la marque — la bande de marque disparaît et **`Objectives` devient le titre de page** (`pageTitle`) ; le head du rail de Cockpit reprend ce mot.

### Créer et ajuster un objectif ([`objective-modal.js`](../../src/components/objective-modal.js))

Une modale, deux modes, un **brouillon mis en scène** : rien ne touche le Playbook avant **Create objective** / **Save changes**. L'objectif se lit comme une **phrase** : « Grow [nom] over a [rolling 30 days | window ending on + date] », puis **Measured by**, chaque mesure une carte labellisée — « Grow from X → Y » (volume) ou « Hold above Y now at X » (rate), la mention **Suggested** + delta (`+22% · +40/day`), « Measured on » = le scope en contrôle ([`measure-scope-field.js`](../../src/components/measure-scope-field.js) : profils groupés par réseau, recherche au-delà d'un seuil, « Every connected profile » réservé aux métriques additives), et « Window » (Same as objective / Rolling 30 days) seulement si l'objectif est fixe. **× retire** une mesure.

- **New objective** (topbar, ou l'empty state) → mode `create`, sur le Playbook actif ; **pas de clause « for <Playbook> »** — le scope est déjà imprimé par la page. Nommer l'objectif le résout en direct : un nom couplé pré-remplit les mesures suggérées, un nom parqué pré-remplit son proxy.
- **Add a measure** fait glisser la même dialog sur le **catalogue** ([`objective-catalog-panel.js`](../../src/components/objective-catalog-panel.js)) : une seule question, _quelle_ métrique, par familles, les indisponibles grisées avec leur proxy, celles déjà prises marquées. Cliquer **ajoute** — il n'y a plus d'écran configurateur. La carte arrive vide derrière un loader « Reading your last 30 days… » (1,4 s), puis baseline et suggestion atterrissent et la carte reste en bleu 2 s. Save est désactivé tant qu'une mesure se calcule.
- **Adjust objective** (sur chaque objectif) → mode `adjust`, même formulaire ; Save applique rename + mesures + fenêtre en une écriture.
- Écriture : la modale mute l'objet Playbook vivant (`objective[]` + `objectiveMeasures[label]`, un nom en double reçoit un suffixe « 2 »), puis le shell appelle `updateContext(ctxId, { updatedAt: "just now" })` — la notification de `contexts-store` repeint tous les lecteurs. Un objectif créé reçoit `grace: { day: 1, of: 7 }` et `origin: "user"`.

### Les portes vers le chat ([`objective-flow.js`](../../src/objective-flow.js))

Deux verbes par objectif, auto-width : la porte chat (`secondary orange` dans les layouts, `primary orange` dans la topbar de la fiche) et **Adjust objective** (`stroked grey`).

- **La porte chat** porte le `cta` de `nextMoveFor(entry)` : **authored** dans `mocks.objectiveNextMoves` (`ctx-noba::Sales`, `ctx-acme::Brand awareness`, `ctx-acme::Lead generation`), sinon **dérivé de l'état** — collecting → « Plan it in a chat », on track → « Double down in a chat », sinon → « Fix this in a chat ». `openObjectiveInChat(entry)` arme le handoff `pendingObjectiveChat` (`{ key, ctxId, label }`) et navigue vers `/session/new-<ts>?contextId=<ctxId>&title=<label>` : le chat naît lié au Playbook de l'objectif et nommé d'après lui.
- **Repurpose** (sur chaque post lié) → `repurposePostInChat(entry, post)` : le même handoff, avec `post: { excerpt, network, date, contribution }`. Pas de passage par le board des winners : ces posts ne sont pas dans `top-posts-store`.
- À l'arrivée, `session.js` consomme le handoff et appelle `startObjectiveChat` : Archie ouvre sur le **diagnostic** (`opening` authored, ou générique), puis un **Quickpicker** « Where should I start? » (angles authored, ou trois par défaut — What should we publish? / What worked so far? / Draft 2 posts for it). Pour un repurpose, Archie **cite le post** avec ce qu'il a fait, puis « How should I build on it? » (Draft 2 more like it / Why did it work? / Adapt it elsewhere). Chaque choix passe par `sendMessage`.

### États vides

- Aucun Playbook → « No Playbook yet ».
- Playbook sans objectif → « No objectives on <marque> yet » + **New objective** ; la bande de marque (le switcher) reste au-dessus quand le flag workspace est OFF, sinon une marque sans objectifs serait une impasse.
- Objectif sans post lié → « No post I drafted has moved this objective yet. Start a chat about it to draft some. »

### Le seed

9 Playbooks portent des objectifs (`objective:` dans `mocks/playbooks.js`), dont des parqués (Lead generation, Sales, Product adoption) qui démontrent le proxy. Next moves authored pour 3 objectifs, posts authored pour 6 (`ctx-noba::Sales`, `ctx-acme::Brand awareness`, `ctx-acme::Lead generation`, `ctx-customer::Brand awareness`, `ctx-founder-voice::Build personal brand`, `ctx-agorapulse::Product adoption`) ; le reste passe par les générateurs déterministes. Baselines, cibles et trends par Playbook sont choisis pour que la même marque raconte la même histoire partout (Noba : Link clicks 126 / 300 = 42 %, en baisse de 11 %).

## 20. Clips — la vidéo d'abord, les posts à la fin (flag `clipsSpace`, défaut OFF)

**Pourquoi.** Le travail sur les clips était éclaté sur quatre surfaces — le Clip Studio (une session `clip-studio-*` qui rendait la main au chat), l'onglet Clips du panneau, la modale Video Clips (trim + sous-titres), les questions de draft dans le fil — et le **crop editor** de la prod (`content/studio/playgrounds/crop-editor`) n'existait nulle part. Quelqu'un qui vient pour faire des clips a maintenant un espace centré là-dessus et rien d'autre : on part de la vidéo, on fait tout le traitement, et les posts viennent à la fin. UI classique façon Opus Clip / Vizard — pas de conversation dans l'espace. Flag OFF : le Clip Studio, la modale Video Clips et le flow de clips du chat, inchangés.

**L'objet : la Video** ([`videos-store.js`](../../src/videos-store.js)), rangée dans la bibliothèque du Playbook (`playbookForNewWork()`), **hors de tout chat** — la 4ᵉ exception de [CONCEPTS](CONCEPTS.md) §3. Elle possède ses clips ; les drafts faits depuis eux vivent dans `posts-store` sous `video-<id>`.

**L'ordre est celui de la prod** (`content/studio … handlers/video-clips.ts`) : l'ajout lance l'analyse **tout de suite** (pas d'écran de réglages), on revoit et on choisit les moments, **puis** les options (`set_clip_options` : ratio → sous-titres → CTA), le compte, les posts. Règles reprises : **3 clips** jusqu'à 10 min, **10** au-delà ; vidéo de **30 s à 2 h** ; **5 ratios** (`RATIO_IDS`) ; les **8 presets** de sous-titres de la prod + None (`PROD_PRESET_IDS` dans `clip-captions.js`). Les chips posées une par une deviennent des contrôles d'UI réglables quand on veut.

Tout l'espace est le **DS clair**, construit avec ses seuls composants : seule la vidéo se lit sur un **puits noir** (moniteurs, aperçus, vignettes, lecteurs). ⚠️ Un mode sombre (`body.clips-space`, la rampe `--app-vc-*`) a été essayé puis **retiré le 2026-10-26** — ne pas le reproposer. **Hiérarchie des actions** : un seul `primary orange` par écran, l'action qui clôt (Get clips · Write N drafts · Schedule N · Create draft) ; `primary blue` pour une étape (_Write posts for N clips_) ; le reste en `stroked grey` / `ghost grey`. Retirer un clip et supprimer un draft passent par le **confirm modal** (_« Remove this clip? »_ / Remove, _« Delete this draft? »_ / Delete, Cancel) — pas de toast Undo.

### `/clips` — la bibliothèque ([`library.js`](../../src/screens/clips/library.js))

- **Premier passage** (bibliothèque vide) : un **hero** — à gauche le titre (« Turn a long video into clips »), le lien YouTube / Drive + **Get clips** (orange), **Upload a video**, la règle de durée (« or drop a file here · from 30 seconds to 2 hours ») ; à droite la **vitrine**, sur le puits noir : **un exemple dit tel** (tag DS _Example_, « A 52-minute podcast, cut into 10 clips ») — le podcast seedé (`exampleVideo()`, hors du store), ses dix clips posés sur la vidéo (trois à l'encre), puis trois clips **recadrés pour de vrai** avec leur titre ; celui du milieu **joue tout seul** (`data-autoplay`, coupé par `prefers-reduced-motion`), les autres au survol. Dessous, le parcours en trois étapes (`buildWorkflowFlow`, le même bloc que les studios).
- **Dès qu'une vidéo existe** : le hero devient une barre _Add a video_ (« I'll cut it into short clips, framed and subtitled, ready to post. ») sans vitrine ni étapes, et **Your videos** (avec son compteur) suit juste dessous. Chaque carte : vignette (jouée au survol, muette), durée, la **carte des clips** au pied de la vignette (où ils tombent dans la vidéo), nom, « Added Oct 28 », les faits nommés en texte (« 10 clips », « 2 drafts », « 1 scheduled »), puis **ce qu'elle attend**, en bleu avec une flèche (le clic y mène) : _Pick clips and write posts_ (aucun draft) · _Schedule N drafts_ (→ l'étape 2) · _Write more posts_ (tout est planifié) · _Add a clip_ (plus aucun clip). En analyse, un voile sur la vignette porte l'étape et le pourcentage, patchés en place.
- Un fichier se dépose **n'importe où sur le hero** (un cadre « Drop your video to start » le confirme) ; il est **lu pour de vrai** (object URL), sa durée vérifiée avant l'analyse (`lengthProblem`). Un lien est servi par une vidéo beta de remplacement (`standInForUrl()` : le proto ne lit pas YouTube). Les deux vidéos seedées sont les cas beta du crop editor de la prod, streamés depuis le CDN library beta ; le cas YLE (vidéo client prod) est écarté. En mode démo, l'ajout est désactivé.

### `/clips/:id` — le projet ([`project.js`](../../src/screens/clips/project.js))

- **Analyse** : l'aperçu de la vidéo, « Finding the best moments », quatre étapes (Uploading → Transcribing → Finding highlights → Framing speakers, `ANALYSIS_STAGES`), « You can leave this page… » ; dessous, _Your N clips land here_, un emplacement 9:16 par clip à venir (3 ou 10), sur une ligne, qui respire à tour de rôle (figé sous `prefers-reduced-motion`).

- **Deux étapes, pas deux onglets** : le **stepper DS** **1 Pick the clips** (« · 2 of 3 ») › **2 Write the posts** (« · 3 drafts ») — `?tab=drafts` pour l'étape 2.

Puis une ligne (« Tick the clips to turn into posts. Click one to open it. ») et chaque clip (vignette recadrée, numéro, durée, titre) avec **sa case — une seule notion : poster ce clip** ; un clip non coché s'estompe ; la vignette et le titre sont un bouton qui ouvre le clip, cerné de bleu. Plus aucun clip : « No clips left. » + Add a clip ;

### `/clips/:id/edit/:clipId` — l'éditeur unique ([`editor.js`](../../src/screens/clips/editor.js))

Quatre éditeurs n'en font plus qu'un : **à gauche la rail d'outils puis le panneau de l'outil**, la scène à droite, **une timeline pour tous les outils** en bas. Chaque contrôle est là où il agit : ce qu'on choisit (l'outil, ses réglages) à gauche ; ce qui façonne l'image (format, safe area) sur le moniteur Output ; ce qui agit sur le temps au-dessus de la timeline.

- **La rail** compte **cinq outils** (`EDITOR_TOOLS`) — Reframe, Transcript, Subtitles, Text, Brand — et suit les items du left nav (survol blue-10, outil courant blue-20 et blue-150, gras, jamais de barre de bord). L'outil courant est dans l'URL (`?tool=`). ⚠️ Deux anciens outils l'ont quittée : **Trim** n'existe plus (la plage est fixe ; `?tool=trim` ouvre Reframe) et **Clean up** est la tête du Transcript (`?tool=cleanup` ouvre Transcript). Le transcript est un outil comme les autres, plus une colonne à part : la scène garde la même largeur dans tous les outils. La première fois, une infobox DS en tête du panneau, _How this editor works_ (« Pick a tool on the left. - **La scène** est faite de **moniteurs encadrés**, comme Source et Program dans un logiciel de montage, chacun sa barre et son image sur noir : **Source** (sa taille, son timecode en temps de la vidéo) et **Output**. Reframe les montre côte à côte, séparés par une poignée qu'on glisse (ou ←/→ quand elle a le focus, de 30 à 80 %) ; les autres outils, l'Output seul. Le **format** n'est pas un outil : c'est un réglage du cadre, dans la barre de l'Output (« Video · Vertical 9:16 ▾ » par défaut, « This clip · Square 1:1 » quand le clip a le sien), à côté du **guide de zone sûre** (« Safe area · TikTok zones ▾ » — TikTok / Reels / Shorts zones, chacun avec le logo de son réseau, ou No guide avec un œil barré : où les boutons du réseau couvrent l'image ; le logo se pose hors de ces zones). Quand le moniteur est étroit (Reframe), les deux selects perdent leur libellé en ligne. **Changer le format** recadre depuis l'auto (un cadrage vaut pour un format) : si le cadrage a des retouches, _« Change the format? »_ le demande d'abord (Cancel garde le format).
- **Au-dessus de la timeline** : la lecture (▶, « temps du clip / durée du clip »), puis **« At the playhead »** et deux boutons `stroked grey` qui disent leur objet — **Split part here** (**S** ; Reframe seulement — un nouveau découpage du cadrage, le clip reste entier) et **Add text here** (ouvre Text, la tête de lecture sur le texte ajouté). ⚠️ Des icônes nues dans les en-têtes de piste ont été essayées (on ne savait ni ce qu'elles faisaient ni qu'elles agissaient à la tête de lecture), comme un « Split » seul dans une barre commune (il se lisait « couper le clip ») : les en-têtes ne portent que le nom de la piste.
- **La timeline** est une fenêtre sur la vidéo : sa **règle lit le temps de la vidéo** ; ce qui vit dans le clip (parties de cadrage, textes) se lit en temps du clip. Trois pistes — **Clip** (la forme d'onde, lisible dans la fenêtre du clip, voilée hors de lui ; les cartes Intro / Outro ; ce que le cleanup a caché, en marques), **Framing** (les parties, les coupes caméra), **Text**. Le **début et la fin du clip sont écrits sur ses bords**, dans la règle, en lecture seule (la règle omet les graduations qu'ils couvriraient) : ⚠️ **la plage d'un clip est fixe une fois le clip créé** (2026-10-29, comme la prod) — ni Start / End clip here, ni touches I / O, ni poignées, ni glissé du corps, ni temps tapé sur un bord. Un clic sur une piste place la tête de lecture ; sa **pastille** se saisit ; les parties de cadrage se choisissent dans Reframe seulement (ailleurs, la piste s'estompe, inerte, et sa légende disparaît) et un clic y met la tête là où on clique. Les **frontières** entre parties se glissent (une étiquette dit le temps, « 0:08.6 · on the cut » quand elle colle à une coupe) ; une prise qui ne change rien ne laisse rien à annuler. **Joindre deux parties** : un bouton apparaît au survol de leur frontière, ou **Join with the previous part** dans le panneau. Sous les pistes, la légende « Grey: my framing · White: yours » et **Snap to camera cuts** (toggle DS).
- **La barre du haut** suit l'organisme Top bar : retour · le titre (style h2) · un crayon qui ouvre le **rename modal** (un renommage n'est jamais inline) │ **Undo** / **Redo** (boutons texte `ghost grey` — en icônes, ils se lisaient « pivoter ») · **Save** (`stroked grey`, désactivé tant que rien n'a changé) · **Create draft** (`primary orange`, le dernier : enregistre, ne coche que ce clip et ouvre l'étape 2). La rail de l'app s'efface (`body.clips-editing`). Quitter avec des changements : _« Save your changes? »_ — **Discard changes** / **Save and leave**. Clavier : Espace lit, S coupe, ←/→ avancent d'une image, ⌘Z / ⇧⌘Z.
- Les resets disent tous « Reset … » (Reset part, Reset all parts, Reset to the video's style, Reset to the Playbook's look) ; « Back to … » ne sert qu'à naviguer.

### Les portes

- La ligne **Clips** de la rail (`ap-icon-video`, compteur = les vidéos du Playbook).
- Le starter **Extract video clips** (home, chat neuf) → `/clips`.
- Depuis un chat : la carte « N clips to review », le menu d'une source vidéo (**Open in Clips**) et _Edit clip_ sur un draft du chat importent la source **une fois** dans la bibliothèque du Playbook du chat, avec ses clips, et ouvrent la vidéo — ou directement l'éditeur du clip ([`open-in-clips.js`](../../src/screens/clips/open-in-clips.js)). Le chat garde ses clips.
- **Branding › How your clips look** sur la fiche : le preset de départ, le logo et son coin, intro / outro. Sauvé à chaque changement, comme le look image.

`npm run check:framing` vérifie le moteur de cadrage sur les deux vidéos seedées.
