# Stores & state management

Pas de librairie externe (Redux, Zustand, etc.). Le proto a son propre pattern minimaliste documenté ici.

## Pattern de base

Un store per-session suit cette structure :

```js
import { createSessionNotifier } from "./store-utils.js";

const state = new Map(); // sessionId → state
const notifier = createSessionNotifier("storeName");

function seed(sessionId) {
  // lazy seed depuis mocks/, sauf en mode new-alt
  if (isNewUser()) return emptyState();
  return mocks.byId(sessionId) ?? emptyState();
}

function get(sessionId) {
  if (!state.has(sessionId)) state.set(sessionId, seed(sessionId));
  return state.get(sessionId);
}

export function getX(sessionId) {
  return get(sessionId).x;
}
export function setX(sessionId, x) {
  get(sessionId).x = x;
  notifier.notify(sessionId, get(sessionId)); // shallow notify, le snapshot est celui du store
}
export const subscribe = notifier.subscribe; // subscribe(sessionId, fn) → unsubscribe
```

Un catalogue global fait pareil avec un array (ou une `Map` par id) et `createNotifier(label)` → `{ subscribe, notify, count }`.

Voir [`src/store-utils.js`](../../src/store-utils.js) : `createNotifier()` et `createSessionNotifier()` (abonnés par session, `subscribe` / `notify` / `clear(sid, finalSnapshot)`), chacun appelant ses abonnés dans un try/catch. Le per-session l'utilise partout (`posts-store`, `post-plan-store`, `assistant`, `composer-mentions`, `composer-connector`, `inline-question`, `sidebar-wizard`, `batch-studio`, `clip-studio`, `context-builder`) ; deux fan-outs restent écrits à la main : `library.js` (il réémet les sources de `sources-stream`) et les abonnés aux sources de `sources-stream.js` (ses uploads passent par `createNotifier`). Un id neuf vient de `newId(prefix)` (`utils.js`), jamais d'un compteur local.

## Les globaux du listening

La plupart des stores sont per-session (Map<sessionId, state>) — `sources-stream` compris : ses sources sont scopées au chat qui les a créées, seuls ses **uploads** (état transitoire d'avant-source, que la modale lit comme un pool) sont globaux. `library.js` re-émet par session pour que les écrans abonnés à `library.subscribe(sid)` repaint quand une source landed.

Les vrais globaux sont les **catalogues** — ils préexistent à tout chat : `contexts`, `connectors`, `folders`, `sessions`, `schedule`, `schedule-presets`, `top-posts`, `videos`, et les deux stores du listening ci-dessous. Voir [`CONCEPTS.md` §3](CONCEPTS.md#3-à-qui-appartient-quoi).

**Deux stores, et les deux sont globaux.** Un feed apparie un Playbook à des sources et tourne sur une cadence ; un Topic appartient à ce feed et arrive dessus — l'un comme l'autre bien avant qu'un chat existe pour l'accueillir. Rien de tout ça n'est per-session, et c'est ce qui les met du côté des catalogues.

**Le feed est scopé, donc ses compteurs le sont.** Le compteur de la ligne Topic Feed de la sidebar est le nombre de Topics **à revoir** (`countToReview`) d'un seul feed, pas une somme sur tout le compte : la surface qu'il envoie ouvrir n'en montre qu'un. Quel Playbook, ça vient de `playbookForNewWork()` ([`active-playbook.js`](../../src/active-playbook.js)) : le Playbook **actif** sous le flag `playbookWorkspace`, le Playbook par défaut sinon (repli : le premier Playbook visible) — la même résolution que l'écran vers lequel le compteur envoie, pour qu'ils ne puissent jamais nommer deux marques différentes. Flag OFF, `?pb=` dit la même chose et s'arrête à son écran ; flag ON, la rail porte le scope et `?pb=` n'est plus lu. ⚠️ Un scope **caché** (un select de barre de filtres qui écrit le Playbook actif, sans switcher visible) a été essayé et écarté — ne pas le remettre.

**Aucun scan au boot.** La file du Topic Feed est seedée pleine, avec un vrai étalement de statuts et de groupes d'âge : la fraîcheur se lit dans la donnée, pas dans une arrivée rejouée à chaque rechargement.

## Le store ne filtre pas : `playbook-access`

[`playbook-access.js`](../../src/playbook-access.js) n'est pas un store — c'est une couche de prédicats **au-dessus** de `contexts-store`. Le partage aurait pu être implémenté en filtrant `getContexts()` ; ça a été écarté pour une raison précise.

Un chat dont le Playbook a cessé d'être partagé doit encore pouvoir le **nommer** : _« ce chat tournait sur Brightline · launch, et Jonas Beck a arrêté de le partager »_. Écrire cette phrase demande de lire une fiche qu'on n'a plus le droit d'ouvrir. Un store filtré rendrait ce bandeau impossible — il faudrait dupliquer les noms ailleurs, ou renoncer à la phrase.

Donc : **le store tient les faits, ce module tient les droits.** Les surfaces substituent `visibleContexts()` / `usableContexts()` / `editableContexts()` à `getContexts()`, et `revokedContextFor()` est le seul autorisé à regarder par-dessus la barrière. Le flag est court-circuité en un seul endroit (`on()`), donc flag OFF = tout permis.

Corollaire pour les mocks : les stores de contenu (`posts-store`, `library`) construisent leur set « est-ce un chat de démo à seeder ? » depuis `mocks.allSeedSessions`, pas depuis `recentSessions` — sinon le chat seedé sous flag arrive avec des panneaux vides.

## Invariants

### 1. Subscribers ne fail jamais le notifier

`createNotifier()` et `createSessionNotifier()` wrappent chaque subscriber dans un `try/catch` et `console.warn` en cas d'erreur. Un subscriber broken ne tue pas les autres. Les deux fan-outs écrits à la main (`library`, les sources de `sources-stream`) n'ont pas cette garde.

### 2. Le couplage entre stores est borné (et listé)

Imports d'un module à état vers un autre (les imports de `mocks.js`, `store-utils.js`, `utils.js`, `user-mode.js`, `feature-flags.js` et `demo-mode.js` sont omis sauf mention) :

- `library.js` → `assistant.js` (et injecte `setIdeasReader(getIdeas)` dans `assistant`, pour éviter le cycle inverse) + `sources-stream.js` (`getSources`, `subscribeSources`, `pushScriptedSource`, `completeScriptedSource`).
- `composer-mentions.js` → `library.js` (+ `components/idea-card-compact.js`).
- `assistant.js` → `connectors-store.js`, `posts-store.js` (`addPostDraft`), `sources-stream.js` (`getSources`, `subscribeSources`), `mention-flow.js` (`offerMentions`) (+ `components/toast.js`). ⚠️ `mention-flow.js` réimporte `assistant.js` : un cycle, résolu parce que l'appel n'a lieu qu'à l'exécution.
- `topic-feeds-store.js` → `contexts-store.js` (+ config `topics-catalog.js`).
- `topics-store.js` → aucun store (config `topics-catalog.js` seulement).
- `videos-store.js` → `contexts-store.js`.
- `active-playbook.js` → `contexts-store.js` + `sessions-store.js` (+ `url-state.js`).
- `contexts-store.js` → `org.js` + `languages.js` + `voice-parts.js`.
- `sources-stream.js` → aucun store (`url-services.js`, `components/toast.js`).
- `modules/image-studio/state/store.js` → `state/playbook-brand.js` + `services/index.js` (`storageService`) ; `playbook-brand.js` → `contexts-store.js`, `active-playbook.js`, `playbook-access.js`.
- Sans dépendance vers un autre store : `sessions-store`, `connectors-store`, `posts-store`, `post-plan-store`, `composer-connector`, `schedule-store`, `schedule-presets-store`, `folders-store`, `top-posts-store`, `feedback-store`, `social-profiles`, `org`.

Règle : une arête nouvelle s'ajoute à cette liste dans le même commit, et ne crée jamais de cycle (`library` injecte `setIdeasReader` dans `assistant` précisément pour ne pas en créer un). Les flow orchestrators (`draft-flow.js`, `context-builder.js`, …) restent le lieu où l'on compose plusieurs stores.

### 3. Lazy seed

Un store ne crée jamais d'entrée pour une sessionId tant que `getX(sid)` n'a pas été appelée. Évite la fuite si on liste 100 sessions dans la sidebar mais qu'on n'en ouvre qu'une.

## Singleton warning

Le système `?v=N` du cache-bust **rend deux imports avec versions différentes équivalents à deux modules séparés**. Conséquence :

```js
// fichier A.js
import { getSessions } from "./sessions-store.js?v=12"; // instance #1

// fichier B.js
import { getSessions } from "./sessions-store.js?v=13"; // instance #2 — !!
```

Les deux instances ont leurs propres `state` Map et `subscribers` Set — deux copies du store, avec des états qui divergent. C'est arrivé plusieurs fois sur `main`.

D'où la règle actuelle : **un seul numéro pour toute l'app**, réécrit en une passe.

```bash
npm run bump            # N → N+1 dans src/ ET dans index.html
npm run check:versions  # échoue si un ?v= diverge — lancé par le hook pre-commit
```

`scripts/cache-version.mjs` détient le numéro. Ne jamais éditer un `?v=` à la main : le sed manuel oubliait systématiquement les `import("…")` dynamiques (`right-panel` → `session.js`, les `toast.js` paresseux…), et c'est exactement là que la divergence se logeait.
